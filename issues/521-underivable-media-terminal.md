# 521 · 画脸谱的「死欠账」：源图损坏 / 缺失的图每轮都被算作待描述，点开始生成却全跳过

来源：用户实测（2026-09-30，承 520）——「20 张待描述，我点击开始生成，直接全部跳过，又开始生成其人。
其人这块儿生成是不是不管有没有数据都会跑一遍？」

用户拍板（2026-09-30）：
1. **坏档补坏档的标注、缺失补缺失的标注**（两类分开）；
2. **这件事在第一次导出媒体的时候就应该做**——不在补画时才补救，不给后续留遗留问题；
3. **描述段零进展时加短路 + 明确告知**，不再把画像段跑一遍。

## 根因

### 一、两类「不可用」都发生在 prep 侧，但都没落账

- **缺失**：`bz_prep.py` 段 3（map）本就在逐条比对「消息引用的图 ↔ 磁盘上的解码产物」——
  `rel = disk.get(hexs)`；`rel` 为空时它**静默 `continue`**（不写进 `image_map.json`）。
  于是该消息的 `img` 保持 chat 原始值 `<月>/<hex>`（**无扩展名**），插件的描述段拿它拼
  `desc/<月>/<hex>`（无后缀）→ 永远读不到档。
- **坏档**：段 2（derive）对源图 `Image.open` 抛异常时**只计 `fails` 账本**（`derive["fail"] += 1`），
  产物表里不留痕迹；插件侧于是把它当普通欠账。

### 二、描述段把「读不动派生档」当成了「本批没事做」

`runDescribeStage` 的批循环里：`descDataUrlOf` 全返回 null → `led.doneBatches = i + 1; continue`
（注释写的是「不烧调用，计完成跳过」）。结果：**整段零调用走完、账本显示 17/17 批完成，而聊天仓里
那 20 张 `text` 依旧为空** → 欠账口径（`pendingMediaCounts` 说 20 张）与批完成口径（全完成）互相矛盾。

下一轮补画：仍是 20 张待描述 → 点开始生成 → 又是「全部跳过」→ **永远不收敛**。这正是用户看到的
「直接全部跳过」。

### 三、确诊路径还有一个副作用

描述段跳过 ≠ 整链停：`prep`（媒体全 skip）→ `describe`（零调用）→ 采集批 → **其人 / 相交 / 纪事 /
档案提炼固定 4 次调用**照跑。用户那次只有 1 条新增素材，5 次调用纯白烧。

## 决策

### A. prep 侧新增权威旁路表 `media_fail.json`（issue 521 决策 1：在导出那轮就落定）

段 3（map）末尾一次性写出 `<数据根>/<联系人>/media_fail.json`，数组，元素：

```json
{"file": "<月>/<名>", "reason": "missing" | "broken", "ct": 1754394429, "sid": 2952…}
```

- `missing`：消息引用了图片，但磁盘上没有可消费的解码产物（源图没导出 / `.bin` 没解出来）；
- `broken`：磁盘上有产物，但本轮 derive 段打不开（段 2 把失败项记进集合，段 3 比对时归类）；
- `file` 对 `missing` 是 chat 原值（可能无扩展名），对 `broken` 是产物名——两者都同时带 `ct` / `sid`，
  与 `image_map.json` 同口径，插件按 `sid` 优先、`ct` 兜底匹配。

**写入守卫**：`--limit > 0`（调试半轮）时**不写该表**——半轮结果会把「没轮到」误判成「缺失」，
而缺失是终态。表缺失 = 无权威，插件不动标注。

### B. 插件侧两类终态标注（决策 2）

`descSkip` 从「唯一取值 sensitive」扩为三种：`'sensitive'`（服务商拒绝，ADR-0224）、
`'broken'`、`'missing'`。`isDescSkipped` 语义随之变为「是否已是终态跳过」（三种都算）：

- 不算欠账（`pendingMediaCounts`）、不切批、不进 refs——待描述归零，不再每轮重扫；
- 图片页签格子上分别显示 `源图损坏` / `源图缺失`（与 `敏感` 并列），**不给解除入口**——
  坏档/缺失是磁盘事实而非启发式判定，没有误伤也就没有「重试」的意义；
  title 说明「重新导出媒体后会自动重试」，撤销语义由表的权威性承担（见下）；
- **表即权威（自愈）**：并仓时把当前标着 `broken` / `missing`、但不在最新表里的图**清掉标注**
  ——用户重导媒体、源图修好后，下一轮 prep 自动把它放回可描述队列，不需要手工撤。

### C. 描述段「有欠账、零可读」直接收尾（决策 3：用户拍板）

`runDescribeStage` 新增终态返回 `'unreadable'`：有欠账（`pendingCount > 0`）但整个图片集**一张派生档
都读不动**（零调用）。`runJob` 收到即收尾为 `done`、不再进画像段，并明确告知：

> 「丘羽」本次没有可提炼的内容：20 张图片的源图损坏或缺失，无法生成描述

判据收窄的理由：B 落地后，死欠账已不再是欠账，**「有欠账、零可读」只剩两种成因**——本轮刚导入、
派生还没跑起来，或磁盘/数据根临时掉线。两种都该停下来说清楚，而不是继续烧 4 次成文调用。

## 不做

- 不重试/修复坏档本身（源图是微信备份里就坏的，插件无从修）；
- 不给 `broken` / `missing` 做「解除」按钮（撤回语义由 `media_fail.json` 权威性承担，按钮只会
  把用户送进「解除 → 又跳过 → 再标注」的空转）；
- 不改敏感标注（ADR-0224）的判定与撤回入口。

## 验收

1. 真数据：对丘羽重跑一次 `bz-face prep` 后，`media_fail.json` 恰好覆盖那 20 张（17 坏档 + 3 缺失；
   另 6 张源图正常的在其他联系人名下）；
2. 并仓后 `pendingMediaCounts` 对全库归零，图片页签逐张可见 `源图损坏` / `源图缺失`；
3. 源图修好再重导一次，标注自动清掉并回到可描述队列（自愈）；
4. 描述段「有欠账、零可读」时任务收尾为 done + 明确提示，且**零画像调用**；
5. `--limit` 轮不写 `media_fail.json`。
