# 528 · 录音孤儿轮次：删了原件，仓里的转写轮次清不掉

## 背景（用户原话）

> 「再报一个非常严重的bug，大琳，我删除了录音之后，并入的录音统计还是410条，没有被删除」

## 实况（只读解锁保库复核）

| | 值 |
|---|---|
| `大琳/recordings/` | **目录空**（mtime `2026-09-29 08:40` 本地） |
| 仓内 `rec:大琳 周一 10点40分✔️.aac:*` | **410 条**轮次仍在 |
| `kindCounts.录音` | `410` |
| `stats.recordingCount` | `410` |

全库普查（25 位已入库联系人）：**只有大琳这一位**是孤儿，410 条全来自那 1 个文件；
其余人 `recordings/` 与仓内轮次一一对应。所以不是普遍性数据事故，但这个**洞**是普遍性的。

## 两层根因

1. **时间长线**：原件是 `2026-09-29 08:40` 没的，而「删除同时清仓内轮次」的 ADR-0221 决策 1
   落地于 `2026-09-29 15:15`（提交 `227b3ee1`）——**早了 6 个半小时**。早上那次删除走的是
   旧口径（只删文件、不清仓），仓内 410 条轮次就此成了孤儿。已部署产物（`main.js` 9/30 19:55）
   里清理逻辑是在的，所以这不是「产物陈旧」。

2. **结构性根因（这才是要修的）**：两个集合之间没有任何一致性约束——
   - **行的集合** = `readdirSync(recordingsDir)`（`ui.ts suppRecState`）；
   - **统计的集合** = 仓内 `rec:*` 消息（`datasource.ts storeStatsOf`）。

   原件一旦不是通过删除入口消失（外部删除 / 旧版本删除 / 同步覆盖），仓内轮次就同时满足
   「永远参与统计」+「**永远没有删除入口**」——行随文件一起消失，没人能再点它。
   ADR-0221 决策 3「上锁即不删」只防住了**将来**的删除，救不了**已经发生**的孤儿。

> 讽刺的是 ADR-0221 的「背景」节原文就点名了这个风险：
> 「若删了原件却漏删仓内轮次，那些轮次就再也没有清理入口了（行已不在，没人能再点它），
> 而它们仍在参与统计与画谱素材。」——防住了自己的删除路径，没防住别人删文件。

## 方案

见 `docs/adr/adr-0228-recording-orphan-turns-and-row-set.md`。要点：

1. **行集合 = 磁盘文件 ∪ 仓内已并入文件名**（`suppStoreInfo.mergedRecs`），差值即孤儿行。
2. 孤儿行照出：徽章「**源已失**」、行上注明「原件已不在磁盘 · 仓内 N 条转写轮次仍在统计与素材」，
   列表上方挂一条提示块说清「为什么统计退不掉、去哪清」。
3. 孤儿行**只留「删除」**（不给改起点 / 查看轮次：原件与 sidecar 都不在了）；
   删除复用既有 `suppDeleteRecording`，不为孤儿新开路径。
4. 确认面板改文案、去掉「同时删除录音原件」勾选（原件早就不在）。
5. **不自动清理**（沿用 Q3「只报不清」口径）：给入口、说清代价，清不清由用户点。
6. `storeStatsOf` 一个字不改——统计永远如实反映仓里的事实。

## 验收

- [x] 原件不在磁盘、仓里有轮次 → 该行出现在原声页（修复前完全不出现）
- [x] 徽章「源已失」+ 行上「仓内 N 条转写轮次仍在统计与素材」（N = 用户看到的那个数）
- [x] 页头提示块报条数 + 说清去哪清；没有孤儿的人不出块
- [x] 孤儿行不给「改起点」「查看轮次」，给「删除」
- [x] 确认面板：报清仓内条数、不给「同时删除录音原件」勾选
- [x] 点确认 → 仓内轮次清零 + `kindCounts.录音` 归零 + `stats.recordingCount` 归零 + 行与提示块消失
- [x] 原件还在磁盘时**不**出孤儿行（别把正常行误标成源已失）
- [x] `tsc --noEmit` 干净 + 全量 `vitest` 全绿

## 顺带发现的遗留（另开 issue，不在本次范围）

`closePeoplePanel` 复位了 `suppImgDelPending` / `noteDelPending` / 编辑态（`clearProfEditState`），
但**没有**复位录音侧的 `recDelPending` / `recStartEditFile` / `recRefConfirm`，也没有复位 `suppOwnerId`
（而这三个态的复位块挂在 `suppOwnerId !== detailId` 分支里）。后果：**关面板再打开同一个人，
上次那个「确认删除」框 / 改起点编辑态 / 重建质心确认框还挂着**——同一个删除框，用户可能以为
是新弹出来的而误点「确认删除」。测试里已撞到（用例间会互相污染），暂由用例自己收尾绕过。
