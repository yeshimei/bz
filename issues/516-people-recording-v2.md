来源：用户七点需求（2026-09-29）+ grill 四轮拍板（同日：第 1 轮 16 条 / 第 2 轮 8 条 / 第 3 轮队列化 /
第 4 轮现场报错 + 段落化，见各轮小节）。
关联：ADR-0212（补充素材入口与数据路径）、ADR-0213（分离管线与轮次进仓）、ADR-0214（工具收编）、
**ADR-0216（旁音过滤）**、**ADR-0217（起点一等化）**、issue 509 / 510 / 511 / 512（录音线一期）。
域：people（脸谱）+ `tools/obsidian-face`（bz-face 包）。

## 背景（一期实况，读源码核实，非推测）

1. **去重**：只有「同名不覆盖」（`ui.ts suppAddRecordings`，`existsSync(target) → continue`）。
   不同名同内容 → 两条都进库；换名重导 → 同一段录音在时间线上**出两遍**
   （轮次消息 key = `rec:<文件名>:<轮序>`，文件名换即新前缀）。
2. **第三人语音无人管**：管线是**两态** Viterbi（我 / 对方），没有"都不是"的出口。
   `?` 只在 `mean_abs_llr < FLOOR(0.05)`（两质心分不开）时出现——第三人语音往往 |llr| 很大，
   会被**很自信地**判成我或对方。VAD（fsmn-vad）只对**语音**响应，纯音乐 / 环境噪声基本已被它拦掉，
   真缺口是「电视里的人声」这类第三人语音。
3. **质心来源**：`bz-face refs` 从**微信语音**建（`chat.json` type=34 的 who 标签 × `voice/*.wav`），
   **不是从录音建**。"先建质心"的前提是该联系人已做过数据源导入；没做过则 refs 产不出。
4. **起点日期**：`recordingTsOf` = 文件名解析 → **mtime** → now。`大琳 周六 10点14分✔️.aac` 解析不出
   日期 → 回落 mtime = **复制到 recordings 那一刻**，错得离谱。且录音行**既看不到也改不了日期**
   ——`suppRecTs`（ui.ts）只声明、只 clear、只 get，**零写点**，ADR-0212 写的"时间可改"从未实现；
   轮次绝对时间 = 起点 + 偏移，起点不准则全歪。
5. **删除**：录音行**没有任何删除入口**（仅 处理 / 续跑 / 重试 / 并仓 / 停止）。
   `<数据根>/.bz-face/rec-control/<联系人>/<文件名>.control.json` **无人清理**（只有停止时写入）。
   已并仓消息带 `rec:<file>:` 前缀可定点清除，`storeStatsOf` 可重算统计。
6. **重进程并行**：`startRecordingTask` 的注册表（`running` Map）允许**同时多条**；一条录音一个进程，
   每个进程各自 `AutoModel` 冷加载 vad / CAM++ / SenseVoice（数 GB 内存 + 分钟级）。用户实测
   **两条并发**（截图：「录音处理 · 2 条在跑」两条都停在"启动模型…"）= 内存与 CPU 双重浪费。
7. **口径**：术语「插件册」= **聊天仓**（保库记录里的消息流）；「脚本册」= **sidecar 账本**（`.turns.json`）
   + **控制文件**。用户所说"录音事件范围"按域内既有 **录音轮次（Recording Turn）** 的起止理解。

## 第 1 轮拍板（16 条，2026-09-29）

### 一、去重（点 1）

- **Q1 判据 = 只做文件字节 sha256**（用户明示"只做 a"，否掉"时长相同→解码抽样指纹"第二级，
  也不引 chromaprint）。理由：真人操作里绝大多数重复是"同一文件复制 / 改名"。
  **知情项**：换容器 / 转码 / 裁剪产生的"同音频不同字节"抓不到，不做提示。
- **Q2 同名分支**：同名 + 内容相同 → 跳过并**单列**提示"重复 N 条"（不再混在"都已在库里"里）；
  同名 + 内容不同 → **落位加 ` (2)` 后缀，两份都留**并提示。静默丢文件是数据损失，比多一条脏录音严重。
- **Q3 存量重复**：只**巡检 + 横幅提示**（"库里有 N 组重复，点开看"），**一条都不自动删**。
  重复的两条可能一条已并仓一条没有，自动裁决必然削数据；删原件不可逆。

### 二、旁音过滤（点 2）

- **Q4 判据 = 绝对相似度门限**；**Q5 落点 = 留账 + 不进仓**；**Q6 门限 = 自适应**（refs holdout 分布落 npz meta）。
  三条已成型为 **ADR-0216**（含：轮级后过滤而非三态 Viterbi、只在 dual 启用、取向宁可漏滤、
  `?` 口径不动）。术语新词：**旁音（Side Speech）**。

### 三、质心前置（点 3）

- **Q7 缺质心 → 串行前置**：点「处理」时若 ref 缺失，先跑 `refs` 再起 `rec`（同一任务链，
  进度块上行显示"建质心 → 转写"）。理由：降级跑完再重跑要白付一遍声纹 + 转写（76 分钟录音是小时级），
  而 refs 只有几分钟。
- **Q8 refs 产不出**（没做过数据源导入 / 语音样本太少）→ **照跑降级（不拦）**，
  并把原因说人话（"该联系人还没有微信语音素材，质心建不出来——先做数据源导入再回来重建"）。
  与 ADR-0213"任何降级不阻断导入"一致。

### 四、起点与标注（点 4）

- **Q9** 标注载体 = 原件旁生成人类可读逐轮时间轴（`<名>.turns.md`）+ 录音行「查看轮次」入口。
- **Q10** 起点升格为导入时确认的一等数据（解析不出必填、可改、落盘）。
- **Q11** 改起点回写已并仓消息 ts，不自动改写已生成的脸谱正文。
  三条已成型为 **ADR-0217**（含落 `recordings/<名>.meta.json` 而非 sidecar、mtime 作上界、
  过滤清单单源、turns.md 由插件写且含旁音轮）。

### 五、单条删除（点 5）

- **Q12 原件取舍**：删除弹窗给勾选「**同时删除录音原件**」（**默认勾选**）。
  勾 = 整条消失（用户原意）；不勾 = 只清仓消息 + 账本，行回落「待处理」可重跑
  （因为录音页按 `recordings/` 目录列行，留原件必然回到待处理——这是必须显式化的连锁）。
- **Q13 清单与确认强度**：清 录音原件 / `.turns.json` / `.turns.md` / `.meta.json` / `.tmp` /
  `rec-control/…/<文件名>.control.json` / 仓内 `rec:<file>:*` 消息 + kindCounts & stats 重算。
  确认走**真弹窗二次确认**（弹窗列明代价），**不上主密码门**——录音原件来自用户自身磁盘，
  删掉我们的副本不等于素材灭失，与"删整条保库记录"代价不同级。
- **Q14 进行中与已画谱**：处理中 / 排队中的行**不给删除**（先停止 / 移出队列）；若该联系人
  **已画过谱**（复用现有 `deleteTierOf` 判据），弹窗加一行告知"已生成的画谱正文不会随之改写，
  要反映删除需重新画谱（花钱）"，不自动重画。

### 六、错人预检（点 6）

- **Q15 = 导入时预检（复制前）**：每个文件抽 3 段各 3 秒嵌一次——与对方质心匹配良好 → 放行；
  与我质心匹配良好 → 放行；**两者都不像** → 警告"这条录音里没听到你或 <联系人> 的声音，可能选错了"，
  弹「仍然导入 / 跳过」。无质心时跳过预检（不拦）。每文件几秒。
  **不做**"与全库其他联系人质心比对"（要多存全库质心、成本高、只能抓"录的是别人"抓不了"是哪一位"）。

### 七、其他方向（点 7）

- **Q16 采纳 a / b / c / g / h**：a 录音行显示起点日期；b 「查看轮次」入口；c 时间线锚点
  （形态见第 2 轮 Q22）；g 开录音页提示"有 N 条中断可续跑"；h refs / rec 失败原因落成可读诊断。
- **不采纳**：d 长录音轮次折叠 / 只并高信息量轮（动口径、风险高，等实际用一段再定）；
  e 已并仓后"删原件省空间"独立入口（Q12 勾选已覆盖）；f 进仓后人工校正单轮文本（另开一批）；
  i 批量处理 / 批量删除（队列化后本就不需要批量入口——连点几条「处理」即排队）；
  j 阈值等做成设置项（算准的值直接固化，不把调节权当交付物）。

## 第 2 轮拍板（8 条，全部按推荐，2026-09-29）

- **Q17 元数据落点 = 独立 `<名>.meta.json`**（不进 sidecar）：sidecar 是脚本账本，而"要重转就删
  `.turns.json`"会连起点一起删掉——起点是用户确认过的输入，不该被"重转"清掉。
- **Q18 旁音实现 = 轮级后过滤**（不动 Viterbi）：保两态 97.6% 校准资产；旁音粒度本就是轮级。
- **Q19 门限取松（宁可漏滤）**：holdout `max-sim` 最小值再留余量；误杀由「查看轮次」复核兜底。
- **Q20 me-only / blind 不判旁音、不做错人预检**（显式不做，不是"做错"）。
- **Q21 `<名>.turns.md` 由插件写**（并仓成功时生成、起点变更时幂等重写），内容 = 全轮含旁音。
- **Q22 时间线锚点不新造消息**，由 UI 给每条录音的**首轮**渲染录音头。
  理由：`media.ts` 现在就把 `[录音 …]` 前缀解析成轮次（算进"录音 N 段 / 总时长"与画谱素材计数），
  新造同前缀消息会**污染这套解析**；UI 头还能带"点击展开全部轮次"，比一条消息更有用。
  副作用（知情）：锚点只存在于面板时间线，数据侧的锚由 `turns.md` 承担。
- **Q23 建质心阶段的「停止」= 直接杀进程**：npz 是原子写（`.tmp.npz → os.replace`），半途杀掉不留半截，
  重跑重来；给 refs 加 control 要发包改脚本，收益不抵成本。该阶段显示"建质心中…"（无百分比）。
- **Q24 「`?` 不确定轮」口径不动**（照旧进仓、落对方侧）：方案 C 下"不确定时长 ≈ 0"，
  改它收益极低口径面却大。知情的有偏项，注释写清。

## 第 3 轮定稿（重进程串行化，2026-09-29）

用户实测截图「录音处理 · 2 条在跑」→ 要求**改成队列、不并行，UI 同步改**；
随后追加 **「画谱在跑，不能跑录音，录音在跑不能跑画谱」** → **推翻此前的 (a) 推荐，取跨域互斥**；
并选「待命进程算占闸，起录音前先杀它」。全部成型为 **ADR-0218**。

- **N1 = 跨域重进程闸门**，粒度 = **整条画谱任务**（含 AI 段；知情吞吐代价——录音最长等到整条任务跑完，
  故必须有可见等待状态与出口）。
- **N2 = 不持久化**（内存队列，重启即清）；续跑依据**永远是 sidecar**，队列只是会话级节制器。
- **N3 = 停当前一条 + 队列自动继续**，另给「清空队列」（两个正交动作：这条不对 / 腾机器）。
- **N4 = 待命 prep 进程算占闸**；录音抢占时先协作式终结它（写 `stop` 控制文件，超时兜底
  `abortPrepSession`），提示"恢复画谱任务时会重新加载模型"。
- 已定细则（不占问题位）：串行粒度全局一条（跨联系人）；入队即返回，行状态 **`queued`**；
  **出队那一刻才判是否需要质心前置**（前面任务可能刚建好质心，入队时判会白建）；
  排队行文案「排队中 · 第 N 位」+ 「移出队列」；进度块 `录音处理 · 1 条在跑 · N 条等待`；
  排队中 / 处理中**不给删除**（Q14）；画谱侧 `runQueue` **`await` 闸门释放而非 `break`**
  （保住 `whenIdle()` 语义：有任务等闸时不能提前 resolve）。

## 第 4 轮拍板（2026-09-29：现场报错 + 一条新需求）

### A. 录音处理**最后一个阶段**报错（WinError 5）

现场（用户截图）：

```
大琳 周一 10点40分✔️.aac  →  失败
PermissionError: [WinError 5] 拒绝访问。:
  '…\recordings\大琳 周一 10点40分✔️.turns.json.tmp'
  -> '…\recordings\大琳 周一 10点40分✔️.turns.json'
```

读源码 + **实测**得到的实况：

- 脚本 `save()`（`bz_rec.py:114`）= 写 `.tmp` → `os.replace`（原子落账）；转写**逐轮落账**
  （`bz_rec.py:324-348` 每轮一次 `save`）→ 76 分钟录音数百次 replace。
- 插件每秒读同一 sidecar：`tickRecRows`（每行一次）、`renderNote → recNoteRows`（每秒再一遍）、
  `suppRecState`（每次册画页把每行读一遍）。
- **实测根因**（`.scratch/rec-tmp-lock/`：Node 持一个读 fd + Python 反复 replace 同一目标）：
  **21 次尝试 21 次全 `WinError 5`**——Node 只要持有读句柄，replace 全程被拒。根因是 libuv 在
  Windows 开文件**不带 `FILE_SHARE_DELETE`**，而 replace 要覆盖目标就必须能删它。
  **确定性，不是竞态运气、不是杀毒软件。**
- `save()` 无保护 → **任何一次碰撞整个脚本崩**；但**转写成果不丢**（逐轮已落账），
  丢的只有收尾 `phase:"done"` 与统计段。

定稿 → **ADR-0219**：脚本侧重试（多次 × 短退避 + tmp 名带 pid）+ 终失败给人话诊断；
插件侧**降读压**（轮询先 `stat` 判 mtime/size 变化，变了才读内容——`stat` 不占读句柄）；
**完成度兜底**：停在 `transcribe` 但**全部轮次都有 text** → 视为完成，可直接并仓。

### B. 轮次段落化（新需求）

用户："录音数据合并，连续时间范围内只有一个人说话合并成一条数据"。

- **A1 断段规则 = 纯同人连续，无时间间隔阈值**（用户明示）。知情：同一人隔久（同一段录音内）再说
  会并成同一条，段跨度 / 时长可能远大于净说话时长。
- **A2 存量已并仓的不自动重并、也不给「重新分段」入口**（用户明示）；新口径只对**新处理 / 重新并仓**
  生效。理由：重并会改动聊天仓 → 已烧过批的画谱任务被指纹判废（`DRIFT_ERROR`）要重新画谱、重新花钱。
  老录音若要新分段：删仓消息（Q12 不勾原件）→ 行回落「待处理」→ 再处理。
- 我直接定的细则（不占问题位，觉得不对就推翻）：**空转写轮**不输出但**不断开**；旁音 / `?`
  因说话人不同而**天然断开**；`ts` = 段首轮、`dur` = 段跨度、情感**全一致才带**否则省略、
  文本各轮直连；key = `rec:<文件>:s<段序>`；`turns.md` 与「查看轮次」仍**逐轮**并标段界。

定稿 → **ADR-0220**。

## 落地调整（写代码时发现，非决策变更）

- **Q22「时间线录音头」改落点**：决策原文是「UI 给每条录音的**首轮**渲染录音头」。实况是
  **面板根本没有消息流列表**（三折页 = 其人 / 相交 / 纪事，都不是原始消息流；唯一消费
  `store.msgs` 的 UI 是录音页签的计数）。所以没有「首轮渲染」的落点。
  改为落在**「查看轮次」预览的头部**（那条录音的 `文件 · N 轮 · 并成 M 段 · 旁音 K`）——
  Q16c 的本意（长录音几百轮不好回溯）在这里被满足，且这是人真正读轮次的地方。
  不新造消息这一条（Q22 主决策）照旧。
- **Q3 重复巡检的代价控制**：没有按原话「扫一遍 recordings/ 把重复组报出来」无脑全量哈希——
  改成**先按文件大小分桶、只有同尺寸 ≥2 个才读盘算 sha**。正常录音时长各异 → 绝大多数情况
  一次盘都不读；册页重画不会被拖慢。判据（字节 sha256）与导入去重同源，没换判据。
- **T9 段界标记**：`turns.md` 与「查看轮次」都加了段界（ADR-0220 §7 要求），且判据收成
  **单源函数 `recordingTurnSegments`**（与并仓的 `segmentRecordingTurns` 同构，有单测锁住两者
  不许漂移）——否则「预览说 3 段、仓里出来 4 条」这种口径漂移没人拦得住。
- **删除必须「要么都清干净，要么不动」**（ADR-0221 决策 3）：上锁时写不了仓，若照样删原件，
  仓里的 `rec:<文件>:*` 轮次就成**清不掉的孤儿**（行由 `recordings/` 驱动，文件没了就没有删除入口），
  且继续参与统计与画谱素材。故上锁时整条不删，只提示解锁。
- **T2 巡检的判据与导入去重必须同源**：`duplicateRecordingGroups` 的 sha 入参默认就是
  `fileSha256`，只有「同尺寸 ≥2」才真读盘。两处判据漂了会出现「导入说重复、巡检说没有」。
- **T10 抽检走录音队列**（ADR-0218 决策 10）：`bz-face check` 是第三种 funasr 消费者，
  与 rec / refs 同闸；且**一个进程查完所有待导入源文件**——每条起进程会白付分钟级冷加载。
  存疑只打标不硬拦（「仍然导入」放行），无质心 / 只有 me / 抽检失败一律 `unknown` 放行。
- **T6 抢占 latch 的真死锁**（写码期发现并修）：抢占请求「发过就别再发」若以「试过」为条件，
  画谱任务真在跑时那次返回 false 就把标志锁死，等任务跑完只剩待命进程持闸 → 录音**永久等下去**。
  latch 条件必须是 `preempt() === true`（成功）。另有两条闸门泄漏边：`runner` 同步抛错、
  会话复用走早返回——都已配单测。
