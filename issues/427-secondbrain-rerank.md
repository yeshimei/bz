# 427 · 第二大脑检索加交叉编码重排（Qwen3-Reranker + AI 面板「启用重排」开关）

- 状态：已实现（2026-09-24）
- 用户原话①：「Qwen3 家族提供了专门的 Qwen3-Reranker 模型（同样有 0.6B/4B/8B 版本）。你可以先用 Embedding 进行初步向量召回，再用 Reranker 对 Top-K 结果进行更精细的交叉编码打分与重排，典型场景下可额外提升 5%-15% 的准确率。」
- 用户原话②：「按照8b的」
- 用户原话③：「在设置的AI面板里面，为它专门设置一个开关选项，默认开，当选中 Qwen3 8b 模型时才会显示这个选项」
- 用户拍板（AskUserQuestion）：生效范围 = **全部链路统一生效**（参考面板 / 对话 / 自动关联 / 每周撞车）；失败兜底 = **静默回退余弦序 + 控制台 warn**；模型档位 = **4B**（8B 在本机 12GB 显存上无法与 8B 嵌入共驻，见下「实测」）
- 关联：ADR-0186（本票决策固化）/ issue 425 + ADR-0185（分数单尺：重排只改名次、不改分数）/ issue 422 + ADR-0182（Embedding 模型迁入 AI 面板，本票开关同组）/ issue 424 + ADR-0184（同组前三行现状）/ ticket 46（检索级 10s 超时降级）/ ticket 111 + 118（自动关联管线与全文查询）/ issue 360（每周撞车）/ ticket 103（VectorStore 检索链路）
- 号位说明：426 之后取 427；ADR 取 0186

## 背景与目标

现状检索是**单塔**：查询与笔记段各自嵌入后算余弦（issue 425/ADR-0185 起为精确全扫）。单塔模型的通病是「查询与文档从不互相看见」——语义相近但答非所问的段落常常挤掉真正对口的段落。

**交叉编码重排**（cross-encoder）把 (查询, 候选段) 拼成一对送进同一次前向，逐对打分后重排，是检索里最标准的第二段增益手段。本票把它接到现有召回之后。

## 关键约束：Ollama 没有 rerank 端点，只能借 logprobs 打分

- `POST /api/rerank`、`POST /v1/rerank` 均 404（Ollama v0.34.3 实测）；
- 可用通道 = `/api/chat` + Qwen3 官方 yes/no 模板 + `logprobs: true`，取首 token 上 yes/no 两类 logprob 归一化成 **P(yes)** 作为相关分；
- **不做 yes/no 文本二值降级**：二值分只有 0/1 两档，并列全按余弦序排（等于没重排），且「余弦尺 / 二值尺」混用正是 ADR-0185 刚清理掉的问题。拿不到 logprobs 就整轮判失败、回退余弦序。

**踩坑（实测）**：本模型是 Qwen3 **思考模板**转换版，不加 `think: false` 时首 token 恒为 thinking 标记；配 `num_predict: 1` 根本走不到 yes/no → 拿不到 logprobs → 每次都静默回退，重排形同虚设。请求体必须显式关思考。

## 实测（12GB 4070 本机，证据脚本 `.scratch/rerank-probe/probe.mjs`）

### 一、显存：8B 重排与 8B 嵌入无法共驻（这是换 4B 的唯一原因）

| 模型 | ctx | 显存 |
|---|---|---|
| qwen3-embedding:8b | 8192（默认） | **7.19 GB** |
| Qwen3-Reranker-8B Q4_K_M | 8192（默认） | **9.6 GB** |
| Qwen3-Reranker-4B Q4_K_M | 40200（模型自带默认） | 10.08 GB |
| Qwen3-Reranker-4B Q4_K_M | 8192 / 4096 / **2048** / 1024 | 7.5 / 5.07 / **3.86** / 3.17 GB |

- 8B 重排 + 8B 嵌入 = 16.8GB ✗；把 8B 的 ctx 压到 1024 也仍有 12.57GB ✗ → **每次检索都要换入换出**：嵌入重载 3.1–4.4s + 8B 重排重载 3.9s（4B 默认 ctx 下更达 15.0s），20 条重排合计 ≈ 9.7s，**紧贴 `SEARCH_TIMEOUT_MS` 10s** → 参考面板/对话会频繁「超时 → 降级纯文本检索」，比不加重排更差。
- 用户据此拍板换 4B：**4B@ctx2048（3.86GB）+ 8B 嵌入（7.19GB）= 11.05GB 共驻成功**（`ollama ps` 两条同时 resident），检索不再有换入换出。

### 二、延迟（4B@2048 共驻、暖态）

| 阶段 | 实测 |
|---|---|
| 查询嵌入 | 71–134 ms |
| 全扫 + 取池 | 12–26 ms |
| 重排单对 | p50 64–104 ms（max 149 ms） |
| 重排整轮（9–18 条） | 885–1171 ms |
| **一次完整检索** | **≈ 1.0–1.3 s**（10s 上限内，余量充足） |
| 冷启动首对（含 4B 载入） | 3.1–3.3 s（落在 6s 整轮预算内，仍是「跑得完」） |

### 三、分数与名次（同一份 225 笔记 / 3193 chunk 真实库）

- **有真关联时区分度极好**：查询「松果体」→「褪黑素」**0.916**、「长期晚睡晚起与抑郁症互为因果」0.564，其余候选 ≤0.008（余弦侧它们是 0.437/0.405/0.354——单塔分不出真假，交叉编码一步分开）。
- **无真关联时是噪声序**：查询「熬夜血糖」整轮最高仅 0.083；「区县筛选」给出 0.667/0.488 的排序，但库内并无对口内容（余弦侧本身也只有 0.42 上限）。⇒ 重排分**只有相对次序有意义，不是概率、不是阈值**。
- **名次变动**：18 条候选里 15 条变位、12 条里 12 条、9 条里 6 条；候选**集合**不变（重排只在召回池内换序，不引入新候选）。

## 决策（详见 ADR-0186）

1. **重排是纯换序层**：`hit.score` 仍是原始余弦，名次按重排分。阈值型调用方（自动关联 `linkAgentMinScore` 0.30、每周撞车 0.63）**继续读余弦分**——ADR-0185 的单一分数尺不动。代价：面板百分比可能不随名次单调，这是刻意保留的取舍（另一条路是让阈值改读重排分，那会把「相对次序」当成「绝对相似度」用，更糟）。
2. **生效范围 = 全部链路统一**（用户拍板）：`vectorSearch` 末尾统一接线，参考面板 / 对话 / 移动端 / 自动关联候选 / 每周撞车一起生效，不分叉。
3. **生效条件 = 开关（默认开）× Embedding 模型为 Qwen3-Embedding-8B**：AI 面板「启用重排」行的 `visibleWhen` 与运行期 `rerankActive()` **共用 core `isQwen3Embedding8b` 一条判定** → 行隐藏即不生效，不留「藏着的开关还在起作用」的暗态。
4. **失败静默回退余弦序 + `console.warn`**（用户拍板）：模型未装 / 拿不到 logprobs / 超时 / 预算用尽，一律回退到重排前的顺序；**不触发 `search()` 的文本降级**（那是向量链路故障的降级，与重排这一增强层的失败是两回事）。
5. **整轮预算 6s、单对超时取 `min(20s, 剩余预算)`**：嵌入 + 全扫 + 重排共享检索级 10s 上限；单对超时若恒为 20s，一次挂起就能让整轮跑出 20s+ 把交互式检索拖过上限。
6. **上下文与文本上限**：`num_ctx 2048`（模型自带默认 40200 → 10.1GB 显存，必须显式压）；送重排的查询截 1000 字、候选段截 600 字——交互式查询（面板当前行 ≈300 字）与每周撞车（`WEEKLY_QUERY_MAX_CHARS` 1000）本就在限内，只有自动关联的**全文查询**（上限 8000 字）会被截到标题 + 开篇：**召回仍走全文（ticket 118 口径不动）**，重排看的是笔记开篇与候选的贴合度。
7. **条数上限 `RERANK_MAX_DOCS` = 50**（初版 24，同日 review 收口改；=「参考结果数 TopK」「对话参考结果数」的设置上限 1–50——任何合法 TopK 下列表整列同尺，初版 24 在 TopK 调到 25–50 时会复现用户原始投诉的「两把尺」观感）。**二轮 review 收口：超过上限的列表整轮不重排**（原「超出部分保持余弦序接在重排段之后」的分段结构退役）——建链候选池 `max(TopK×3, 24)` 可达 150，分段会让那些调用长期停在半重排（名次两段混排 + 每篇白付 ~1.7s GPU），而不重排对它们的产出零影响（它们自己按 score 重排/取 max）。串行逐对调用（GPU 单实例下并发不缩短总时长，还会让预算失去意义）。

## 遗留与取舍

- **面板百分比可能不随名次单调**（决策 1 的必然结果）：名次与百分比是两把不同的尺，重排只动前者。（**issue 429 起收口**：灵感参考的桌面面板与移动端列表改为显示 `hit.rerankScore ?? hit.score`，与名次同尺；对话面板仍按余弦。）
- **无真关联时的重排序是噪声**：重排不改候选集合、也不改阈值判定，故不会造成误链；但它会让「本来就都不相关」的列表换个顺序——这是可接受的（那种列表本来就没有正确顺序）。
- **8B 重排在本机不可用的结论只针对 12GB 显存**：换更大显存的机器后，把 `RERANK_MODEL` 换回 8B、`RERANK_NUM_CTX` 放宽即可，其余口径不变（`RERANK_MODEL` 是唯一开关）。
- 探针脚本与实测数据留在 `.scratch/rerank-probe/`（不入 git）。

## 子代理 review 收口（2026-09-24）

- **打分退化分支（应修，已改）**：原实现里「只有首 token 一条 logprob（无 `top_logprobs`）」会退化成 0/1 二值分——每对只落两档、并列全按余弦序，正是本 ADR 明令否决的二值降级，且看起来「已生效」。现改为**必须有 `top_logprobs`，否则按拿不到 logprobs 判失败、回退余弦序**；非有限 logprob（±Infinity / NaN）一律当无效候选跳过，防 NaN 分穿透排序。
- **单对超时注释与实现不符（应修，已改）**：实际生效值 = `min(20s, 整轮剩余预算)`，6s 预算先到、20s 是「单次挂起吞掉整轮」的绝对上限；注释已改正（实测冷载首对 3.1~3.3s 落在预算内，故 6s 不误伤冷启动）。
- **两条代价补记进 ADR**：顺序不敏感的三条链路（建链 / 挂载建议 / 每周撞车）重排不改变产出、只付后台耗时；检索级 10s 超时不 abort 底层链路，面板降级后重排仍可能续跑 ≤6s。
- 未改动项：`scores[i]` 无长度护栏（`rerankScores` 保证等长或抛错，不加冗余校验）；`searchMobile` / weekly 无 10s 包裹（后台链路，预算即上限，符合预期）。

**第二轮（并入 issue 428/429 后）**：见 issue 429「子代理 review 收口」——头部上限 24 → 50（TopK 设置上限，否则两把尺观感复现）、两张面板 resolve 路径加「仍是本轮」门禁、全量回退标题提示。

**第三轮（二轮 review，2026-09-24）**：`RERANK_MAX_DOCS` 的语义从「头部截断」改为「整列上限」——超长列表（建链候选池可达 150）整轮不重排，`applyRerank` 的尾部保序分支删除；「尾部保余弦序」这一结构在本 ADR 里彻底退役（见 issue 429「子代理 review 收口（二轮）」）。
