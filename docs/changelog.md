# 更新日志规范

更新日志不是手写的，是**提交历史的下游投影**：`src/settings-panel/changelog-data.ts` 由
`scripts/_gen-changelog.mjs` 从 git 提交生成，设置面板「更新日志」弹窗与 `manifest.json` 版本号都是它的消费方。
所以写日志的正确姿势是**把提交信息写对**，而不是事后编辑产出文件。

## 硬性标准

**每次 `git commit` 之后，立刻在该提交所在仓库跑 `pnpm changelog`**，并在同一轮内提交产出
（`src/settings-panel/changelog-data.ts` + `manifest.json`）。不得攒着跨票补——攒着必然漏，且版本切点会错位。

跳过仅限：不含 `feat`/`fix`/`perf` 的纯工程提交（`chore:` 产物重出、`docs:` 等），这类提交不进日志。

## 命令与产出

```
pnpm changelog          # = node scripts/_gen-changelog.mjs，仓库根执行
```

| 产出 | 说明 |
|---|---|
| `src/settings-panel/changelog-data.ts` | 生成物，文件头标「勿手改」 |
| `manifest.json` | 最新版本号回写（版本号单一事实源在生成器，勿手改） |

生成器只写这两个文件，其余不动。

## 提交信息怎么写

生成器只吃 `feat` / `fix` / `perf` 三类非 merge 提交，内容取自**主题句**，且会过滤内部工程条目。
因此提交信息直接决定日志长什么样：

- **主题句是给用户看的一句话**，不是给同事看的开发汇报。写「影院按季合并进度条」，不写「评审收口」「补测试」「对齐口径」。
- **Conventional Commits + 域 scope**（如 `fix(cinema): 想看落盘编码 -1，编辑不再弹回在看`）——
  scope 决定条目挂到哪个域标签下，映射表在生成器 `SCOPE2DOMAIN`，新域须同步登记。
- **「——」后的部分作弱化副行**，放可选细节；尾注（issue/ticket/ADR/呈报/原型/自检）与 emoji 会被自动剥掉，写不写都行。
- **会被整条丢弃**：以「评审/走查/深审/收口/守卫/测试/文档/构建/部署/合并…」开头的条目，
  以及正文含「单测/单源/mock/重构/门禁/回归测试…」的条目。落不进日志 = 主题句该改。

## 版本合成规则

- **切点**：主仓库「主构建部署产物」提交日为发版日；该约定（2026-09-08）之前按自然周归并，之后未部署的提交归入生成日。
- **号段前向合成**：首个版本 `1.0.0`；此后每个版本块含 `feat` → 次版本 +1（修订归 0），仅 `fix`/`perf` → 修订 +1。
  判定用**原始提交类型**，不受内容过滤影响。
- **块内上限**：新增 14 / 修复 12 / 优化 8，按主题句去重后截断。
- **空块不展示**（全是内部条目的版本块跳过），但版本链照常推进。

## 连带动作

重跑生成器会改 `src/settings-panel/changelog-data.ts`，**原型新鲜度指纹随之失效**——
须跟着重出原型产物（`node scripts/build-preview.mjs`），否则新鲜度守卫报红。

## 边界

- 只在**主仓库**跑。生成器读的是 cwd 的 git 历史，在 worktree 里跑会生成残缺版本。
- **不手改产出物**。要改文案就改提交信息（必要时 `git commit --amend` 后重跑）；改规则就改 `scripts/_gen-changelog.mjs`。
