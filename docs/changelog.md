# 更新日志规范

更新日志不是手写的，是**提交历史的下游投影**：`src/settings-panel/changelog-data.ts` 由
`scripts/_gen-changelog.mjs` 从 git 提交生成，设置面板「更新日志」弹窗与 `manifest.json` 版本号都是它的消费方。
所以写日志的正确姿势是**把提交信息写对**，而不是事后编辑产出文件。

## 硬性标准

**只在发版时跑**（2026-10-29 起）。日志按 git tag 切块，日常提交没有 tag 就没有版本块——
以前「每次 commit 后跑一次 changelog」的约定随之作废，平时提交只要把信息写对就行。

发版时：`node scripts/_gen-changelog.mjs --next=<版本>`（tag 还没打，版本号由人给），
打完 tag 再跑 `--check` 对账。只有 `feat`/`fix`/`perf` 进日志，`chore:` / `docs:` 不进。

## 命令与产出

```
pnpm changelog          # = node scripts/_gen-changelog.mjs，仓库根执行
```

| 产出 | 说明 |
|---|---|
| `src/settings-panel/changelog-data.ts` | 生成物，文件头标「勿手改」 |
| `manifest.json` | 最新版本号回写（版本号单一事实源在生成器，勿手改） |

生成器只写这两个文件，其余不动。

## 提交信息怎么写

生成器只吃 `feat` / `fix` / `perf` 三类非 merge 提交，内容取自**主题句**，且会过滤内部工程条目。
因此提交信息直接决定日志长什么样：

- **主题句是给用户看的一句话**，不是给同事看的开发汇报。写「影院按季合并进度条」，不写「评审收口」「补测试」「对齐口径」。
- **Conventional Commits + 域 scope**（如 `fix(cinema): 想看落盘编码 -1，编辑不再弹回在看`）——
  scope 决定条目挂到哪个域标签下，映射表在生成器 `SCOPE2DOMAIN`，新域须同步登记。
- **「——」后的部分作弱化副行**，放可选细节；尾注（issue/ticket/ADR/呈报/原型/自检）与 emoji 会被自动剥掉，写不写都行。
- **会被整条丢弃**：以「评审/走查/深审/收口/守卫/测试/文档/构建/部署/合并…」开头的条目，
  以及正文含「单测/单源/mock/重构/门禁/回归测试…」的条目。落不进日志 = 主题句该改。

## 同一版本内的修复：并回那条新功能

日志是给用户看的，用户只想知道**这东西现在是什么样**。一条 `feat` 在同一个版本块里被自己后来
修了几次，最终只该留下**一条、写成修好后的样子**——不要「加了个新功能」下面再跟一串「修它」：

| 别这样 | 要这样 |
|---|---|
| `feat(cinema): 影院加按季进度条`<br>`fix(cinema): 进度条按季取错`<br>`fix(cinema): 进度条跨年又错位` | `feat(cinema): 影院进度条按季合并，跨年不错位` |

日志是提交的投影，所以只能在提交这一侧解决：

- **并进那条 `feat`**：本版内改的还是自己刚加、没发出去的东西，合并回主仓前 `git rebase -i`
  把几条 `fix` squash 进 `feat`，主题句直接写最终态。已经 push 的自己的分支就
  `git push --force-with-lease` 收一下。
- **该保留 `fix` 的只有一种**：修的是**已经发到用户手里**的旧行为——用户真见过那个坏样子，
  这条就是他要的变化。升版之后又引入的回归也算（那一版已经发出去了）。
- 同一版里「加了 X」+「X 用不了，已修」并列，读起来像没测完就发了；用户不需要看你踹了多少脚。

这条只管**同一个版本块内部**。跨版本不管：上一版真坏过，这一版的 `fix` 就该单独写一条。

## 版本合成规则

- **切点 = git tag**（2026-10-29 起）：一个 `v<版本>` tag 一个版本块，块内条目 = `git log <上一个 tag>..<本 tag>`。版本号直接取 tag 名，不再从提交类型推算——同一天发两版、跳号、回退这些边角随之消失。
- **基线 `v1.35.0`**：更早的 tag 与提交不进日志（历史不重写，只是不展示）。基线之前 `--check` 会明确报「基线之后没有版本块」。
- **未发布块**（`--next=1.35.0`）：发版顺序是「先七步出产物、提交、再打 tag」，打 tag 前新版本还不存在，用这个参数把「最新 tag → HEAD」的提交提前算成一个块，版本号由人给。
- **号段**：`feat` → 次版本、`fix`/`perf` → 修订，只对**下一个 tag 该叫几号**有建议意义；生成器不再自己算。
- **块内上限**：新增 14 / 修复 12 / 优化 8，按主题句去重后截断。
- **空块不展示**（全是内部条目的版本块跳过）。

## 连带动作

重跑生成器会改 `src/settings-panel/changelog-data.ts`，**原型新鲜度指纹随之失效**——
须跟着重出原型产物（`node scripts/build-preview.mjs`），否则新鲜度守卫报红。

## 边界

- 只在**主仓库**跑。生成器读的是 cwd 的 git 历史，在 worktree 里跑会生成残缺版本。
- **不手改产出物**。要改文案就改提交信息（必要时 `git commit --amend` 后重跑）；改规则就改 `scripts/_gen-changelog.mjs`。
