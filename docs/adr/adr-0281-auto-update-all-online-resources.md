# ADR-0281 · 自动更新覆盖全部在线资源，顺序固定，且不再节流

日期：2026-11-01 · 状态：已采纳（同日实现）

## 背景

1. 2026-10-30 拍板的口径是「自动更新 = 插件本体 + 三个外部工具包」，手册 / 更新日志 / 索引数据表 / 皮肤要靠用户在设置 → 通用 → 在线资源里逐个点。理由是首启会静默拉 10 MB，其中 9.7 MB 是两个索引（豆瓣影视索引 7.16 MB、RSS 源库 1.91 MB）。
2. 2026-10-31 又给这条链加了 24 小时节流，进一步减少请求。
3. 用户 2026-11-01 的反馈推翻了这个口径：**开着自动更新就该把这些都跟上**，不该让用户分辨「哪些是自动的、哪些要手点」。同时要求有明确顺序——本体最先，日志第二，工具包第三，其余在线资源最后。
4. 上一轮（ADR-0280）已经去掉插件本体检的 24 小时节流；这里把剩下的节流一并去掉，避免「本体每次都查、资源却隔天才更新」的半截状态。

## 决策

1. **`core/auto-assets.ts` 的职责从「工具包」扩到「全部在线依赖」**，固定顺序：
   ① 更新日志 → ② 外部工具包（bundle） → ③ 其余在线资源（手册、归物分类表、RSS 源库、豆瓣影视索引） → ④ 皮肤。
   顺序由代码写死，不跟随清单 `docs[]` 的排列；理由是清单顺序是给设置面板行序用的，不该兼职决定启动链的先后。
   插件本体不在此模块——它由 `core/self-update.ts` 在同一趟启动链里先跑完（皮肤版本区间校验吃 `manifest.json` 版本号，这个先后不能调）。
2. **两条时间节流都删掉**：`core/auto-assets.ts` 的 24 小时（`bz-auto-assets:last-run`）与设置面板在线资源组的 60 秒核对窗。每次启动、每次打开面板都真查一次。
   `autoUpdateAssets` 的 `opts.throttle` 参数随之删除。
3. **保留的合流不是节流**：模块内的 `inFlight`（同一次启动里并发调用只跑一遍）与面板的 `syncRunning`（下载事件逐条扑面时合流重扫）都保留——它们防的是重复劳动，不是限制频率。
4. **判据沿用既有的「本地事实」**：单文件资源比本地文本 sha256（`docStatus`）、目录包看解包标记（`bundleStatus`）、皮肤逐条验 hash（`skinStatus`）。已就绪的条目零请求，只花一次本地读。
5. **版本区间外的条目不动**（`isInVersionRange`）：旧版插件看到「需要更新版插件」的资源，既不下载也不计入统计。

## 后果

- 正面：一个开关管到底。用户不需要知道哪几类资源是自动的；发版后重启一次，日志、手册、索引、皮肤、工具包全部对齐。
- 代价一（流量）：首次安装或资源有更新时，一次启动可能拉满约 10 MB，慢网下会持续几十秒的后台下载。这是用户明确接受的取舍（「用户一天也启动不了几次」）。
- 代价二（本地读）：每次启动为算 sha256 会把已就绪的资源读一遍，豆瓣索引 7.5 MB 那一项最重，实测在几十毫秒量级，可接受。
- 代价三（覆盖）：**皮肤会自动更新**，用户手工改过的皮肤 css 会被清单版本覆盖。此前皮肤只能手点更新，等于默认保护了手改；现在这个保护没有了。要保留手改的话得另做「本地改动不覆盖」的判据，本轮不做。
- 移动端仍整段跳过（没有 Node，工具包下下来也 exec 不了）。
- 测试：`tests/core/auto-assets.test.ts` 整份重写（原第 2 条「在线资源不碰」的回归点反转），新增「顺序固定」用例；`tests/core/self-update-release.test.ts` 的 `throttle: false` 已在 ADR-0280 清掉。
