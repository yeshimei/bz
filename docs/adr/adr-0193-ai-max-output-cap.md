# ADR-0193：AI 输出上限按「provider × 模型」取——面板上界动态、解析出口封顶

- 日期：2026-09-26
- 状态：已采纳（用户拍板「DeepSeek 384K 和智谱 131072 的上限各不一样，你设置一个上限护栏」）
- 相关：issue 457（本票）/ ADR-0148 + issue 334（面板独裁 = 输出上限唯一权威）/ ADR-0151 + issue 342（model-limits 按模型名解析官方档位，本票的基准来源）/ issue 433 + ADR-0190（密钥行「测试」按钮；本票由它翻红✕暴露）/ issue 434（测试状态长在按钮上、不弹详情——故失败原因需从代码侧复现）

## 背景

2026-09-26 用户报「LLM 的智谱 Plan 测试失败」。复现定位到唯一根因：

| 请求 max_tokens | 结果 |
|---|---|
| 200000（面板当时的值） | `400 / 1210 max_tokens参数非法：限制数值范围[1,131072]` |
| 131072（注册表默认） | `200`，回复 `OK` |
| 4096 | `200`，回复 `OK` |

密钥、coding 端点、glm-5.3-flash、`reasoning_effort`、流式与 requestUrl 兜底链路全部正常。

两点放大：

1. **失败面是全域而非单次**：`prompt()` 每次请求都带上解析出的 max_tokens，所以 `aiProvider=zhipu-plan` 时
   日记、小橘、知识库、剪藏摘要等**所有** AI 调用都吃同一个 400；测试按钮的红✕只是最先被看见的症状。
2. **那个上界本身就是假的**：面板「最大输出 token」行的 `max: 200000` 是 2026-09-23 补的**全局硬编码常量**
   （注释自陈「20 万是当前最大上下文模型的量级上沿」），本意只拦「手滑多打几个 0」。它对 DeepSeek
   （393216）偏小、对智谱（131072）越界——**上限是「模型」的属性，不是全局常量**，而 model-limits
   早已收录 `glm-5.3-flash 131072` / `deepseek-flash 393216`，数据在手上却没用上。

## 决策

1. **护栏基准收敛成单一函数 `maxOutputCapOf(providerId, modelName)`（core/ai.ts）**，两级取值：
   ① 该 provider **当前生效模型**（面板「模型名称」覆盖 > 注册表默认）在 model-limits 的官方最大输出；
   ② 查不到则取注册表新字段 `maxOutputCap`（显式声明的官方上限——deepseek 因默认模型名留空、
   查表兜不到，必须显式填）；③ 两者皆无 → `undefined`，即**该通道无官方上限可依、不设围栏**。
   设置面板的输入上界与请求解析共用它，**禁留第二套判定**。
2. **`maxOutputCap` 是「墙」，`defaultMaxTokens` 是「缺省值」**：前者官方核实过、填不超；
   后者回答「未填时用多少」，可被面板覆盖越过——本地模型就是这么用的（Ollama 填 32000 是既有口径，
   本票不回退）。**把兜底档当墙用会误伤无上限通道**，故护栏只在 ①/② 存在时生效。
   本条是本票返工过一次的地方：初版直接拿 `defaultMaxTokens` 当基准，被既有 Ollama 用例挡下。
3. **解析出口封顶 = 唯一的硬护栏**：`getAIProvider` 内，未填覆盖 → 基准优先、无基准回落兜底档；
   填了覆盖 → `min(覆盖值, 基准)`、无基准则不封顶。
   理由：面板 input 的 `max` 只是 UI 软拦——data.json 手改、旧版残留值、跨 provider 换槽都能绕过它；
   而 ADR-0148「面板独裁」已把输出上限的权威定在解析链上，护栏就该长在同一个出口。
   覆盖值为 0 / 负数 / 非数一律按「未填」处理（与面板「填 0 = 清除覆盖」同语义）。
4. **面板上界动态化**：`NumberRow.max` 扩为 `number | ((snapshot) => number | undefined)`，
   两个渲染器（core `settings-schema`、settings-panel `renderer`）共用新导出 `resolveNumberBound` 求值
   （非有限数与 undefined 一律不钳制）；函数型上界挂进各自的刷新链，切服务商 / 改模型名后
   `input.max` 跟着换。「最大输出 token」行 `max: () => providerMaxOutputCap()`。
5. **顺手消一处显示值分叉**：`providerValue('maxTokens')` 原先按**注册表默认模型名**查表，
   一旦「模型名称」行覆盖了模型，面板显示值与请求生效值就会分叉（显示 393216 / 实发 16384）。
   本票改走 `providerMaxOutputCap()`（生效模型名）——显示值 = 生效值。

## 后果

- 填超不再「静默全挂」：面板物理上填不进超限值，手改 data.json 也被解析层封顶。
- 上限随模型走：换模型（「模型名称」行 / 未来新增 provider）自动跟随，面板代码不再需要改。
- **存量超限值不做自动迁移**：本次 zhipu-plan 的 200000 由解析层就地封顶，不擅自改写用户的设置值；
  面板显示值与生效值的收敛发生在用户下次编辑该行时（本票只修了盘上那一处已复现的故障值）。
- **本地 Ollama 不设围栏**（无官方档位可依，`maxOutputCap` 有意留空）：8192 仍只是它的兜底档，
  面板可自由调大（既有口径不回退）。代价是本地通道不享受同类误填保护——但本地是零成本自持服务、
  报错由用户自己看见；反过来把兜底档当上限（初版做法）会直接砍掉本地长输出的可用性。
  日后若某台机器的模型确有档位可查，走 model-limits 补一条即可。
- 新增 provider 的接入成本不变：注册表加一行即带上限（有 model-limits 条目则更精细）。
