# ADR-0187：第二大脑检索取消语义（最新查询胜出；取消 ≠ 失败；空行不查询）

- 日期：2026-09-24
- 状态：已采纳（用户提出「有了新的查询的时候，前面那个查询就中断掉，只查询最新的」，见 issue 428）
- 相关：issue 428（本票）/ issue 427 + ADR-0186（重排接线末端须透穿取消；本 ADR 收口其「不为超时做 AbortSignal 穿透」的遗留）/ issue 425 + ADR-0185（全扫是同步段，取消靠行间检查点）/ ticket 46（检索级 10s 超时降级——失败路径，与本 ADR 的取消路径分开）/ ticket 141（面板失败提示）/ ticket 103（VectorStore 检索链路）/ ADR-0002（依赖方向：`core ← … ← secondbrain`，`core/abort.ts` 为共享层新成员）

## 背景

参考面板/移动面板常驻监听光标，打字与移动光标都会发起检索。此前的语义是「每轮都跑完，谁后返回谁渲染」，于是：

1. 快速改字时一串查询在 Ollama 侧排队（查询嵌入 + 重排整列逐对串行——列表 ≤ 50 条才进重排，暖态 ≈1s/轮）；
2. **旧查询后返回时照样渲染** → 列表内容与光标处文本对不上（本票主诉）；
3. 每轮吃满 GPU，最新一轮压在队尾，「越打字越卡」。

同一时间发现第二个触发面问题：`getCurrentContext` 在光标落在**空行**时会回退取上一行尾 300 字当上下文（对齐 QA 闪念.js 旧语义）——点一下空行也发起一轮与当前编辑动作无关的检索。

## 决策

1. **最新胜出 + 真中断（不变量：列表态归最新一轮所有）。**
   面板持一个在途 `AbortController`（桌面 `ReferencePanel.inflight` / 移动 `MobilePanel.inflight`），发起新一轮前 `abort()` 上一轮；面板/抽屉关闭也 `abort()`（此时已无接管者，让请求跑完纯浪费）。中断**穿透到 HTTP**：面板 → `store.search/searchMobile` → `vectorSearch` → `getEmbedding` / `rerankScores` → `rerankOne` → `fetch(signal)`。不做「只丢弃旧结果、不砍请求」的软取消——那正是排队与卡顿的来源。
   实现上除中断外还有一道正门（同日 review 收口补）：**成功分支先验 `if (this.inflight !== ac) return;`（仍是本轮才收尾）**。被中断的轮次本该在 `await` 处抛错，但底层若忽略了 signal、旧轮迟到 resolve，这道门保证它不把旧列表盖到新轮上——不变量不能只靠「下游都守约」。

2. **取消 ≠ 失败：`AbortError` 走静默收口语义，一切既有降级/提示路径都不得接管。**
   这是本 ADR 的核心约束，四个既有 catch 块都要让路：
   - **面板**：catch 首行 `if (ac.signal.aborted) return` —— 不写「检索失败：请检查 Ollama 服务后重试」，也不追加「⚠ 向量检索暂不可用，已降级为文本匹配」；旧一轮的失败/降级提示挂在已归新查询的列表上只会误导。
   - **`search()`**：不因取消降级文本、不调 `onDegraded`（否则用户会看到「向量不可用」而向量其实好好的）。
   - **`applyRerank`**：不因取消回退余弦序——回填旧序正好会盖掉新查询的列表（这正是本 ADR 要消灭的行为）。
   - **`searchMobile()`**：远程向量一级被取消时直抛，不落 TF-IDF/文本级。
   判定单源 = `core/abort.ts` 的 `isAbortError()`（`name === 'AbortError'`），跨模块不各写一份。

3. **取消与超时必须分开报，且不能只看内层 `controller.signal.aborted`。**
   `httpFetch` / `rerankOne` 各自持一个超时 controller；调用方取消经 `linkAbort()` 把外层 signal 链到它上面。于是「内层 controller 中断」有两个来源（超时、外部取消），**用 `timedOut` 显式标记**区分：取消抛 `AbortError`（静默），只有定时器到点才抛「Ollama 无响应（超过 Ns 未应答）」/「重排调用超时（Ns）」。少这个标记会把用户自己触发的取消报成故障。

4. **检查点落在能被打断的边界上，取消即整轮作废。**
   `vectorSearch`：嵌入前后各一次；全扫是同步段 → `meta.notes` 每 64 篇查一次（相对点积开销可忽略，大库下也不至于「没人要的查询」吃完整个扫描）。`rerankScores`：每对之前查一次（取消后不再发起下一对）。**不做半完成**——不存在「列表已重排一部分、另一部分没跑」的中间态对外可见（重排本就是「整列重排 or 整列不重排」，见 ADR-0186 决策 6）。

5. **面板的取消检查点必须在「查询没变」的早退之后。**
   `refreshContent()` 的早退（`query.length < 2 || query === lastQuery`）先于 `abort()`。顺序反了：用户在原地打空格触发一轮早退，却把在途请求砍了、又没人接手 → 列表永远停在「检索中…」。（移动端 `refreshResults` 相反：先 abort 再判长度——它的短上下文路径**明确清空列表并重绘空态**，终止态自洽，不需要人接手。）

6. **空行 = 无上下文（不再回退上一行）。**
   `getCurrentContext` 整行空白直接返回 `''`。调用方据此短路：桌面面板保持现状（不刷新列表、保留上一份结果），移动端清空参考列表（与它既有的「< 2 字清空」一致）。两端不统一处置是因为既有行为本就不同，本 ADR 只保证「都不发起查询」。副效果：消灭「光标在空行 → 列表显示的是上一行内容的结果」这种对不上的状态。

## 后果

- 快速改字/移光标时列表**只反映最新文本**，不再有旧结果回灌；Ollama 侧不再堆积排队请求。
- 取消是静默的：列表停在「检索中…」直到新查询返回。不弹「已取消」——那是用户自己的连续输入造成的，纯噪声。
- `core/abort.ts` 成为跨域取消语义的共享单源（`abortError` / `isAbortError` / `throwIfAborted` / `linkAbort`）；后续任何面板级「只做最新一件事」需求复用同一套语义。注意 `linkAbort` 返回解绑函数，**必须在 `finally` 里调**，否则外层 signal 会长期持有内层 controller（长生命周期 signal 上泄漏监听器）。
- `getEmbeddingsBatch`（索引侧）也接了 signal 但目前无人传：索引是启动/显式触发的一次性任务，没有「换新查询」语义。留通道是为了不把取消能力焊死在检索侧。
- ADR-0186 的「面板超时后重排仍在后台跑完」这条遗留**部分收口**：面板换新查询/关面板现在会真中断重排链；但**超时**（10s `Promise.race`）仍不 abort 底层链路——超时是失败路径，底层让它跑完最坏只占 ≤6s GPU 预算，而给它加中断会牵动 `search()` 的失败语义，收益不抵复杂度。将来若要收口，入口是 `withSearchTimeout`。
- 取消不改变任何阈值/分数口径：`hit.score`（余弦）与 `hit.rerankScore`（重排分，issue 429）都不受取消影响，被取消的一轮不留任何中间数据。
