# ADR-0211 · 保险库信封密钥结构与快速修改主密码

日期：2026-09-28 · 状态：已采纳 · 关联：ADR-0016（平铺布局）、ADR-0018（提交式加密）、issue 508

## 背景

v1 加密模型：清单与全部密文镜像（正文/附件原始层/预览层）都直接用主密码经
PBKDF2(10 万) → AES-GCM 独立加密。主密码一改，全库镜像都要解密再重加密——
125 文件量级即分钟级 IO 与 PBKDF2 风暴，修改密码功能事实上不可实现。

## 决策

双层信封（用户拍板方向「用户密码只加密入口文件」的工程化）：

1. **每镜像独立 fileKey**：随机 43 字符（64 字符表，≈258bit），镜像本体用
   `CryptoService.encrypt(plain, fileKey)` 加密——密文布局（salt16+iv12+ct）与派生缓存
   全部复用，PBKDF2 开销与 v1 持平（每镜像一次，keyCache 按 salt 兜住重复解）。
2. **清单记住每文件密码**：`keys[ref] = Encrypt(fileKey, masterKey)`；`masterKey`
   为随机 256bit 中间主密钥，`masterWrap = Encrypt(masterKey, 用户密码)`。
   不直接用用户密码包 fileKey 的原因：改密码退化为 O(N) 次重包（百文件 15 秒级），
   经 masterKey 中转后修改密码 = 重包 1 个 wrap + 重加密清单，亚秒级、镜像零接触。
3. **清单本体仍用用户密码加密**：验密语义不变（解密 .safe.enc 成功即通过，GCM 认证），
   `verifyPassword`、解锁屏、销毁确认全部无感。
4. **迁移 v1→v2**（解锁后自动、opQueue 串行、中断安全）：
   新镜像写暂存区 → promote 到顶层（清单仍 v1，旧镜像俱在）→ 清单切 v2 → 删旧镜像。
   任意中断：清单版本裁决一切（v1=旧镜像有效，v2=新镜像有效），残留孤儿由体检清理；
   镜像解密失败即中止保持 v1（完整性优先），下次解锁重试。
5. **公共 API 面零变化**：`SafeManager` 方法签名不变，`keys`/`masterWrap` 只在 data.ts
   内部流转；密码本/脸谱/日记/第二大脑四域无感。

## 后果

- 修改主密码亚秒级完成，不再全库重加密；新增/更新条目只多一次 wrap 登记。
- 清单成为唯一的关键密文：**清单损坏 = 全库不可解**（与 v1 等同，不劣化）；
  体检/自愈对清单的三段式原子写与备份建议不变。
- `changePassword` 在迁移未完成（v1 运行态）时拒绝执行，提示稍后重试。
