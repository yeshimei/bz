# ADR-0166：游戏库「全量落盘 + 媒体全本地化」

- 日期：2026-09-18
- 状态：已采纳（取代 ADR-0163 的「会话内存缓存」取舍）
- 相关：issue 374；前置 ADR-0161（建域）/ 0163（两级缓存）/ 0164（媒体键拆分）

## 背景

用户拍板（原话）：

> 成就图标保存在指定文件夹中，开工吧，所有数据，全量，完整，都存在本地

以及在拍板前明确的一条口径：

> 数据全部存在笔记属性当中，不要 gameshelf.json，图标和图片存在本地指定的文件夹当中

此前 ADR-0163 的做法是「商店标量 + 成就三键进属性；**成就逐条明细与截图 URL 留在会话内存**」，
理由是「详情是看一眼的场景，不是要长期归档的数据」。本次用户推翻该取舍：**要全、要本地、要离线可用**。
按此口径量了一遍真实体量（134 款 / 10088 条真实成就、147 款商店资料）：

| 项目 | 实测 |
|---|---|
| 成就明细（名称\|描述\|态\|日期\|全球率\|apiname） | 全库 800 KB，均 6.0 KB/款，极值 169 KB（PAYDAY 2 1342 条） |
| 其中描述占 64%、名称 24%、全球率 6%、日期 5%、态 2% | 已解锁仅 2411/10088（24%） |
| 成就图标 | 彩色 ~4.1 KB / 灰 ~3.5 KB；两色全下 73 MB |
| 商店截图（前 8 张原图 1920×1080） | 单张 ~420 KB → 全库约 460 MB |
| 用户 vault 现状 | 3315 篇笔记，frontmatter 中位 0.1 KB、**最大 3.9 KB** |

## 决策

### 1. 成就明细进属性（全量，不截断）

```yaml
成就:
  - "合格菜鸟 | 完成你的第一个战役任务。 | 1 | 2021-09-04 | 45.0 | APPROVED_GREENBEARD"
成就已解: 41
成就总数: 69
稀有成就: "…（全球 1.8% 拥有）"
成就更新: 2026-09-18T06:47:00.000Z
```

- 六段定序：`显示名 | 描述 | 已解锁(1/0) | 解锁日期(未解锁 -) | 全球解锁率(未知 -) | apiname`；
- **分隔符用 `|`**：实测 10088 条真实成就的名字与描述里 `|` **零出现**；仍留
  `sanitizeSeg` 把 `|` 换成断竖线 `¦` 兜底——格式契约不能靠「真实数据没出现过」活着。
  引号/冒号/井号交给 YAML 序列化（属性是 Obsidian 写的，不是我们拼字符串）。
- 用**扁平字符串行**而不是嵌套对象：属性面板里字符串列表能逐项就地编辑，嵌套对象只能看；
  且比对象形式小 30%（1145 KB → 800 KB）。
- 第 6 段的 apiname 是图标本地文件的键：用它而不是下标，因为 Steam 追加成就会让下标整体位移。

### 2. 成就图标进本地文件夹，**一个属性键都不占**

```
<海报文件夹>/<appid>-ach-<apiname>-on.jpg    已解锁用彩色（Schema icon）
<海报文件夹>/<appid>-ach-<apiname>-off.jpg   未解锁用灰图（Schema icongray）
```

文件名由 `(appid, apiname, 解锁态)` **推出**，属性里不存路径清单。这一条是属性体积的命门：
134 款的图标地址清单光 URL 就要 1.4 MB（域名 + 40 位 hash），而文件名可推导，一分钱不用花。
代价：图标缺了只能重拉一次 schema 才拿得到 URL → 由 `posters.ts::achIconsMissing` 兜住
（见下「补跑判据」）。两色都下，状态翻转零下载。

### 3. 截图进本地文件夹，两键同序同长

```yaml
截图源:                       # 远端，同步管辖，随库刷新
  - "https://…ss_xxx.1920x1080.jpg?t=…"
截图:                         # 本地，媒体队列写，同步绝不碰
  - "CONFIG/游戏海报/548430-shot-1.jpg"
  - ""
截图更新: 2026-09-18T06:47:00.000Z
```

- **同序同长**，下载失败的位置留空串——下标就是位置，压缩数组会让图与位置错位；
- 张数上限 8（`steam.ts::parseStoreMeta` 的 `slice(0, 8)`）：DRG 有 76 张，全下不现实；
- 下**原图**（1920×1080）而不是缩略图：截图只用于灯箱，600×337 放大后明显糊。
  代价是体积（全库约 460 MB），已向用户说明并留了改口径的余地。

### 4. 详情弹窗改成「属性优先、零网络」

`loadStore` / `loadAchievements` 先读属性（命中即返回、不发请求），只有该块属性缺失才拉网络。
于是「数据都在属性里」这件事有了实际价值：**断网/代理没开也能看全详情**。
新鲜度不在这里管（拉长打开时间是坏事）：
- 打开某款详情时若 `成就更新` 超 24h / `详情时间` 超 14d → **后台静默刷该项**，回来重画；
- 不做全库定时刷新：134 款 × 3 个接口 = 400 请求，每次开面板都跑太重。

### 5. 补跑判据（三件活各自独立）

`backfill.ts::backfillNeeds` + `posters.ts::achIconsMissing`：

| 判据 | 动作 |
|---|---|
| 缺 `详情时间` | 拉 appdetails（含 `截图源`） |
| 有成就页却缺 `成就` 全量列表 | 拉成就三接口（顺带把图标 URL 交给媒体队列） |
| `截图源` 有值而 `截图` 对应位缺 | **零网络**，URL 就在属性里 → 直接走媒体队列 |
| 成就图标文件缺（按当前解锁态那一色判） | 重拉一次 schema 才拿得到 URL |

图标判据只查**当前解锁态那一色**：Steam 个别成就没给 icongray，两色都查会让那款永远判「缺」，
每次开面板白拉一次。

## 后果

- **属性体积**：全库约 1 MB（800 KB 成就 + 200 KB 截图源），均 ~7 KB/款，极值 ~190 KB（PAYDAY 2）。
  相对用户 vault 现状（最大 3.9 KB）明显偏大，但这是一次性的、有上限的（条数由游戏成就数决定）。
- **本地媒体体积**：截图约 460 MB + 成就图标约 73 MB。截图是主要成本，已向用户明示。
- **写入节奏**：`processFrontMatter` 每次整份重序列化，PAYDAY 2 那篇每次回填要重写 ~190 KB；
  回填是一次性的（幂等标记），日常只有「打开详情时的静默刷新」会写。
- 会话缓存保留，但降级为「同一会话内别重复拉」的加速层，不再是数据来源。
- `成就已解/成就总数/稀有成就` 三键保留：让进度条在只有摘要时也能画（旧笔记迁移期）。

## 被否决的方案

- **写 `CONFIG/STORAGE/gameshelf.json`**：会被 Obsidian Sync 同步（该 vault 已有 sync-conflict 残留），
  且用户明确说「不要 gameshelf.json」。
- **嵌套对象数组**（`- 名称: … / 描述: …`）：属性面板不可编辑，体积还大 43%。
- **成就只写已解锁**（94 KB）：丢掉「还差什么」，而那往往才是用户想看的。
- **截图存缩略图**（~60 MB）：灯箱放大后糊，与「完整」的诉求不符。
