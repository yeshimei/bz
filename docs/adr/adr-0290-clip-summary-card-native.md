# ADR-0290：剪藏笔记不写渲染指令，摘要卡改用 Obsidian 原生 callout

- 状态：已采纳（推翻 ADR-0005 第 2 节）
- 日期：2026-11-06
- 相关：ADR-0005（外部依赖策略）、ADR-0082（剪藏本融合域）、ADR-0144（保存物化）

## 背景

ADR-0005 第 2 节当年拍板「按源码的方式写」：保存剪藏时往笔记正文塞一段

````
```dataviewjs
await dv.view(`CONFIG/SCRIPTS/DataView/摘要`)
```
````

由 Dataview 插件执行作者私人库里的 `摘要.js` 渲染摘要。当时插件只服务一个人，这个路径存在，
所以看起来没成本。

现在插件对外分发，这条路变成每篇剪藏都带着一句别人机器上不成立的话：

- 没装 Dataview → 打开笔记就是一段红色报错块；
- 装了 Dataview 但没有 `CONFIG/SCRIPTS/DataView/摘要` → 同样报错；
- 作者自己删/改那份脚本 → 全库旧笔记一起坏。

而那份脚本实际只做一件事：把 frontmatter 的 `summary` 与 `tags` 渲染成一张 `[!summary]`
提示块。也就是说，它没有任何 Dataview 才能做的事，纯粹是属性的另一种显示形式。插件为这一
点视觉效果，把「必须装某个第三方插件 + 库里必须有一份特定路径的私人脚本」变成了剪藏笔记的
隐含前置条件。

## 决策

1. **写侧不写任何渲染指令。** `writeClipNote` 产出 = frontmatter + 正文，正文里不出现
   dataviewjs、不出现指向库内路径的脚本调用。
2. **摘要卡由 auto-summary 在摘要写回成功那一刻生成。** 落点是剪藏笔记正文顶部，形态是
   Obsidian 原生 callout（`> [!summary] 标题` + 摘要段 + `#标签 …` 行）。零插件依赖，
   与旧渲染同形。
3. **写不写卡交给用户。** 设置 · 剪藏本 · 自动摘要组的「笔记内摘要卡」开关（键
   `clipbookSummaryCard`，默认开）。关掉 = 摘要只留 frontmatter 属性。
4. **摘要没生成出来就不写卡。** AI 未配置、请求失败、模型没给摘要——这些分支都不落卡，
   正文不会留一张空壳。
5. **存量迁移。** `scripts/migrate-clip-summary-card.mjs`：扫剪藏目录，把正文开头的旧
   dataviewjs 块换成原生卡（摘要为空则只清旧块、不落空卡）。干跑默认，`--apply` 时先备份到
   `<vault>/.bz-migrate-backup/<时间戳>/`。
6. **读侧兼容。** 右栏剥壳（`stripClipChrome`）同时认旧块与原生卡：未迁移的旧笔记照常读，
   迁移后的正文不会把摘要重复显示两遍。

ADR-0005 第 2 节自此作废，其余两节（AI 配置入设置、Ollama 走 HTTP）不受影响。

## Considered Options

- **继续写 dataviewjs**：把私人库路径固化进所有用户的笔记，且强依赖第三方插件——正是本次
  要修的事故，否决。
- **保存时就把卡写进去**：保存那一刻摘要通常还没生成（AI 摘要跑在保存之后），卡片会是空壳，
  而且之后再也不会更新（正文卡是静态快照，没人回写）。否决。
- **插件自己画摘要卡（自制 DOM）**：笔记里就只剩属性，打开笔记看不到摘要；而 Obsidian 原生
  callout 已经能做到同样的观感，没必要自造渲染层。否决。
- **只写属性、完全不写卡**：最干净、零漂移，但用户明确要求笔记正文能看到摘要卡（2026-11-06
  拍板）。作为开关关掉时的行为保留。

## Consequences

- 老用户库里的旧 dataviewjs 块不会自己消失：要么跑一次迁移脚本，要么在剪藏本里对那篇
  「重新生成摘要」（写回时会顺带清旧块、落新卡）。
- 摘要卡是**写回那一刻的快照**：之后用户在属性面板手改 `summary`，正文卡不会跟着变；
  下次 AI 写回（重跑摘要）才刷新。这是静态卡片的固有代价，换取零依赖与零运行时。
- 开关只控「写」，不负责清理已经存在的卡——担心存量的人应该用迁移脚本，而不是翻开关。
- 摘要卡的标题取笔记 basename（与旧脚本 `dv.current().file.name` 同源）；auto-summary 改名后
  的下一次写回才带上新标题。
