# 0053 — 通知停留时长按字数动态计算

## Status

Accepted（ticket 113，用户需求）。

## Context

ADR-0010 定稿时默认时长固定：info/success/warning 3s、error 5s。实践中长文本通知（如 AI 摘要结果、批量结果汇总）经常来不及看完就消失，用户需留言时长显式传参才能兜底，调用点心智负担高、且容易漏传。

## Decision

`src/core/notice.ts` 新增按文字长度动态计算停留时长：

- **无显式 `duration` 时**：`base + max(0, len − 20) × 60ms`，上限 15s。`len` 为 `msg` + `title` 拼接总字符数（`title` 可空）。
- **≤20 字**：直接用类型默认值（base），短通知行为与旧版完全一致，不影响既有 146 处调用点的既有观感。
- **显式 `duration` 仍优先**（含 `<= 0` 常驻语义），动态计算只兜底未指定的调用。
- **progress 类型不变**：默认常驻，显式 duration > 0 才计时。
- **`setType` 切换类型**不携带文本，沿用类型默认值（消息内容未变，无重新计算必要）；dedupe 合并更新消息时按新消息字重重算。

## Considered Options

- **保持固定时长 + 各调用点自行传参**：拒绝——漏传即回归短显问题，且调用点分散难审计。
- **按行数/换行数估算**：过度拟合——通知正文以单行居多，字符数是更稳定的阅读量代理。
- **按渲染宽度（DOM 实测）计算**：需 in-DOM 测量，与 jsdom 测试环境耦合，且动画入场后宽度才稳定；字符数估算足够逼近阅读时间，拒绝。

## Consequences

- 新增常量 `PER_CHAR_MS = 60`、`SHORT_THRESHOLD = 20`、上限 15000ms，全部集中在 `notice.ts`。
- 长通知（>20 字）停留时间线性延长，用户有充分阅读时间；调用方无需为阅读时长显式传参。
- 既有短通知（实际绝大多数）行为零变化；测试 25 例原样通过。
- 新增 2 例：长文本动态延长、显式 duration 优先。
