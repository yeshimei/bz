# ADR-0163 · 游戏架详情数据两级缓存（frontmatter 标量 + 会话内存）

> 状态：accepted ｜ 日期：2026-09-17 ｜ 相关：issue 370、ADR-0161、issue 368

## 背景

368 建域时详情弹窗只拉两段（成就摘要 + 商店静态元数据），全部写回 frontmatter。
370 把详情扩到「能获取的所有数据」：成就**逐条明细**（名称/描述/图标/解锁时间/全球解锁率，
单款可上百条）、商店**截图**（最多 8 张 URL）、评价正负票、价格、DLC、Metacritic 等。

如果沿用「全部写回 frontmatter」：

- 一款 100 个成就的游戏会给笔记头部加 100 行左右的结构化数据，而 frontmatter 是用户
  在 Obsidian 属性面板里要看到的东西——膨胀十倍后属性面板不可用，用户正文也被推远；
- 截图 URL 是 8 条长串，同样是「看一眼」性质的临时数据，没有归档价值；
- 而成就明细又确实需要能显示。

## 决策

**两级缓存，按「是否有长期价值」切分：**

1. **frontmatter 标量回写（持久）**——商店展示标量（类型/开发商/发行商/发行日期/价格/平台/
   玩法分类/好评率/评测数/好评数/差评数/Metacritic/推荐数/商店成就数/DLC数/简中/简介/官网）
   + 成就三键（`成就已解` / `成就总数` / `稀有成就`）+ `详情时间`。
   价值：**断网或系统代理没开时，详情弹窗仍有上次看到的内容**，而不是一片空白。
   只写「点开过详情」的游戏，不做全库预写（147 款 × 多请求会撞 Steam 限流）。
2. **会话内存缓存（不落盘）**——截图 URL 列表与成就逐条明细。
   重开面板即重拉；明细的排序（按全球解锁率从稀有到常见）也在拉取侧算好。

加载顺序：会话缓存命中 → 直接用；未命中 → 拉取 → 成功写回标量 + 入会话缓存；
失败 → 回落 frontmatter 标量并在弹窗上标「上次同步时缓存的资料」，**不吞错误**。

成就段另有一条短路：`有成就 === false` 的游戏直接跳过三次请求（Schema/Player/全局），
省掉无谓往返。

## 后果

- 用户笔记的 frontmatter 只会长出「可读的标量键」，不会长出几十行数组；
- 重开面板后点同一款游戏会再拉一次（2 请求商店 + 3 请求成就）——接受：详情是「看一眼」的场景，
  不是要长期归档的数据；
- 成就明细与截图在离线时不可见（只有进度条来自 frontmatter 摘要）——如实呈现，不假装有数据。
