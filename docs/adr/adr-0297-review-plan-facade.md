# ADR-0297 · 复习计划对阅读器的读写门面（`plugin.reviewPlan`）

日期：2026-11-11 · 状态：已采纳 · 关联：ADR-0294（readerAi 门面，同一范式）、ADR-0215（知识盒门面）、ADR-0077（复习增强套件）

## 背景

bz-reader 加了「划线 → 复习卡」：把一条划线做成一篇文章放进库里，再登记进复习排期。排期表的钥匙是**文件路径**（`review.json` 里存 `filePath`，复习时直接打开那篇笔记自评），所以阅读器必须做两件事：

1. 在 vault 里写出一份 Markdown 卡片笔记；
2. 把那张卡的路径塞进 bz 的复习计划。

第 2 件是两边关系里**第一次由阅读器反向写 bz 的数据**。此前只有「录入交给你」（knowledge）与「问你只读算力」（readerAi），都不碰 bz 的排期表。

## 决策

1. **另起门面 `plugin.reviewPlan`**，不塞进 `knowledge`：录入的生命周期是知识盒、复习的生命周期是复习域。混在一起，调用方探测「能不能加复习」会拿到一个永远存在的函数，探测就失去意义。
2. 六件事：`isReady()` / `hasNote(path)` / `addNote(path)` / `addNotes(paths)` / `removeNote(path)` / `statusOf(paths)`。
3. **先落盘、再登记**，顺序不能反：`loadItems` 按路径查文件，查不到就标挂起（列表删除线、不进队列）。先登记后写文件只会得到一条打不开的排期。这条口径由阅读器遵守，门面在 `addNote` 里再查一次文件在不在，不在就返回 `notFound` 而不是造悬空条目。
4. **不抛错**：文件不在、已在计划里、路径为空，一律收敛成结构化结果（`{added, reason}` / `{added, exists, notFound}`）。跨插件调用里抛一条异常，阅读器那边只能弹一句看不懂的红字。
5. **批量走一趟读改写**：一次加几十张卡时，逐条 `addItem` 就是几十次全文件读写。`addNotes` 一次 `loadItems` + 一次 `addItems`，并区分批内重复。
6. **`statusOf` 是只读查询、且是门面上唯一的可选动作**：它比「加/删」晚出现，阅读器用 `typeof` 守卫降级——缺了只是不显示「下次复习日期」，不能因此把整个复习按钮判成不可用。返回顺序与入参一致，没进计划的条目给空态而不是省略（省略会让调用方丢掉「第几条对应哪个路径」的对应关系）。
7. 实现走 `src/review/plan-ops.ts`（纯逻辑：只收 `(dm, app, path)`，不碰界面、不碰全局单例）+ `src/review/reader-api.ts`（叶子：只放类型与注册表）。`ensureReview` 注册、`unloadReview` 置 null；`main.ts` 挂的是**常驻转发对象**，每次调用前 `ensureReview`——onload 时域还没初始化，转发让调用方永远拿到稳定的面。

## 后果

- 门面成为对外契约：六个动作的签名变更按破坏性变更对待，调用方以 `typeof` 守卫降级（`reviewOf` 要求前五个齐全，缺一个整块当没有）。
- 阅读器可以选择「只写卡不排期」：没有 bz 时它仍然写文件（卡片本身能当笔记用），只是提示「更新 bz 后可用」。**不承诺**门面能替它建复习域。
- 复习口径（阶段、间隔、FSRS 参数、逾期判定）仍由复习域单一决定，阅读器只消费 `nextReviewDate` 这类结论，不自己算日子。
- 卡片文件归阅读器管：bz 不删它、不重写它，`removeNote` 只摘排期（「移出复习计划」不删用户的笔记）。
