# ADR-0190：Jev 凭据按服务商分存（map 槽位 + 一次性迁移）；密钥行「测试」按钮走真实调用

- 日期：2026-09-24
- 状态：已采纳（用户拍板「切换服务商时 key 和模型名跟着换」+ grilling 四项确认，见 issue 433）
- 相关：issue 433（本票）/ issue 430 + ADR-0188（博查入册——两家共用全局键立刻互相覆盖，本票的直接诱因）/ issue 424 + ADR-0184（Jev 组三行制，行数不变只是绑定换形态）/ ticket 172（LLM `aiModelOverrides` 的 per-provider map 范式，本票照办）/ ADR-0173 + ADR-0181（判定与回落编排零变化）

## 背景

博查入册后，`jevApiKey` / `jevModel` 两个全局键成为两家共用的唯一槽位：换服务商要手工搬值，
忘搬就拿 A 家的 key 打 B 家。同时用户要求密钥行能一键验证连通——「跑一次真的调用」。

## 决策

1. **分存 = 两张 map（`jevApiKeys` / `jevModels`，键 = 服务商 id），不是每家静态键。**
   与 `aiModelOverrides` 同范式：注册表加服务商零 schema/零解析改动，行保持三行制
   （服务商/密钥/模型），密钥与模型行走三函数绑定 + refreshKey——切换服务商显示值原地换槽。
   否决「每家一行 visibleWhen」（LLM 密钥行范式）：行数随服务商膨胀，且 JEV 两行的标签
   （「Jev 密钥」「Jev 模型」）无需区分服务商。
2. **旧键一次性迁入 typesafe 槽位后退役。** 非空才搬（空值搬进去是噪音）；搬运前仍做
   `jev-1.13.0` → `jev-latest` 改写；已有 map 只写 typesafe 槽位。`resolveJevConfig` 是分存键
   的唯一读者——`isJevConfigured` 因此自然修正为「只看当前服务商那格」（此前另一家配了密钥
   也会被误判为已配置）。
3. **「测试」按钮 = 真实调用，不做裸探测。** JEV：`testJevConnectivity` 发一道 noul 小题走
   完整判定链（鉴权/报文/解析全过才算通）；LLM：`testAIConnectivity(providerId)` 走现成
   AI.ask 链路（流式 + requestUrl 兜底，测的就是用户配出来的链路）。成功 = 链路无抛错且回复
   非空（哑响应不算通）；成功/失败均弹通知并带耗时——「连着但很慢」是用户需要的判断依据。
   数据层独立成函数（可单测），schema onClick 只做「落盘防抖值 → 调函数 → 弹通知」——
   **所配即所测**，不测内存里的未落盘值。
4. **测试按钮按行锁定服务商。** LLM 每家密钥行各一颗，按 id 字符串 override 解析（不污染
   全局缓存），与下拉当前选中无关；JEV 单颗测当前服务商。deepseek/智谱的测试是计费调用
   （极小请求，一分钱以下），desc 注明「会发一次真实请求」；ollama 本地零成本。

## 后果

- 换服务商零手工搬值；两家凭据并存后随时切回（`jev-latest` 在博查是别名，模型键甚至不用改）。
- `jevApiKey` / `jevModel` 两键退役：升级后 data.json 由 onload 迁移清理，第三方脚本直读
  旧键的口子（如有）随迁移失效——迁移是单向的，回滚插件版本会丢新槽位里博查的值（可接受：
  旧版本就不认识多服务商）。
- 第三家（如硅基流动 chat 面适配层）加入时：注册表加一行 + map 自动多一格，无新键无新迁移。
