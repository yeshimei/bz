# ADR-0186：第二大脑检索加交叉编码重排（Qwen3-Reranker 4B，纯换序层）

- 日期：2026-09-24
- 状态：已采纳（用户拍板「全部链路统一生效」+「静默回退余弦序 + 控制台 warn」+ 模型档位 4B，见 issue 427）
- 后续修订：issue 428 + ADR-0187（取消语义：面板换新查询即真中断重排链，取消不走余弦回退）/ issue 429（决策 1 的显示取舍与决策 7 的模型单点已收口——`hit.rerankScore` 供显示、`secondBrainRerankModel` 供覆盖）/ 同日 review 收口（决策 6 的头部上限 24 → 50，见下）/ 二轮 review 收口（决策 6 的「尾部保余弦序」结构性退役：> `RERANK_MAX_DOCS` 的列表**整轮不重排**——「要么整体重排、要么整体不重排」；决策 1 的显示尺扩到移动端参考列表）
- 相关：issue 427（本票，含探针实测证据）/ issue 425 + ADR-0185（分数单尺：重排只改名次不改分数）/ issue 422 + ADR-0182（Embedding 模型迁入 AI 面板）/ issue 424 + ADR-0184（同组现状）/ ticket 46（检索级 10s 超时降级）/ ticket 111 + 118（自动关联管线、全文查询）/ issue 360（每周撞车）/ ADR-0002（依赖方向：core ← … ← secondbrain）

## 背景

检索现状是单塔（查询与文档各自嵌入后算余弦）。用户提议引入 Qwen3-Reranker 交叉编码做第二段重排（「典型场景下可额外提升 5%-15% 的准确率」）。

两个前置事实决定了本 ADR 的形态：

1. **Ollama 没有 rerank 端点**（`/api/rerank`、`/v1/rerank` 均 404）。可用通道是 `/api/chat` + Qwen3 官方 yes/no 模板 + `logprobs`，取首 token 上 yes/no 两类 logprob 归一化成 P(yes)。且该模型是**思考模板**转换版——不显式 `think: false` 时首 token 恒为 thinking 标记，`num_predict: 1` 下拿不到 yes/no，重排会永远静默回退（实测踩坑）。
2. **显存放不下两个 8B**（本机 12GB）：qwen3-embedding:8b 占 7.19GB，Qwen3-Reranker-8B 占 9.6GB，8B 档压到 ctx 1024 也仍有 12.57GB——无法共驻，每次检索要多付 ~8s 模型换入换出（嵌入重载 3.1–4.4s + 重排重载 3.9s），20 条重排合计 ≈ 9.7s 直接撞上 `SEARCH_TIMEOUT_MS` 10s，面板会频繁「超时 → 降级纯文本检索」，比不重排更差。**4B@ctx2048（3.86GB）+ 8B 嵌入（7.19GB）= 11.05GB 实测共驻**，暖态一次完整检索 ≈ 1.0–1.3s。

用户据此把模型档位从 8B 改为 **4B**（`dengcao/Qwen3-Reranker-4B:Q4_K_M`），其余设计不变。

## 决策

1. **重排是纯换序层：`hit.score` 仍是原始余弦，名次按重排分。**
   重排在 `vectorSearch` 末尾对已去重、已截断的**整列** `RERANK_MAX_DOCS` 条做（初版 24，同日 review 收口改 **50** ——见决策 6；二轮 review 收口起超长列表整体跳过，不再有「头部重排 + 尾部保持」的分段），只改数组顺序，**不重写 `score` 字段**。于是：
   - 阈值型调用方继续读余弦分——自动关联 `linkAgentMinScore` 0.30（ADR-0146）、每周撞车 0.63（issue 360）口径**零改动**，仍落在 ADR-0185 的单尺上；
   - 面板/对话显示的百分比仍可与阈值、与别的查询横向比较。
   代价是**列表可能不随显示的百分比单调**（一张 31% 的卡排在 42% 前面）。这是刻意保留的取舍：另一条路是让显示分数改读重排分，那等于把「候选集合内的相对次序」当成「绝对相似度」用——重排分既不是概率也不跨查询可比（实测：库里有真关联时能给出 0.916 的强分，没有真关联时同一批候选也照给 0.667/0.488，只是换个顺序）。
   **后续修订（issue 429）**：这条取舍的用户可见后果（面板百分比与名次对不上，用户报「没有按照相关度由高到低去排序」）已按「显示与名次同尺、阈值仍读余弦」收口——重排分另记 `hit.rerankScore` 供参考面板显示，`hit.score` 与全部阈值判定不动（详见「后果」节）。

2. **生效范围 = 全部链路统一（用户拍板）。**
   接线放在 `VectorStore.vectorSearch` 末尾，故参考面板、AI 对话、移动端检索、自动关联候选池、每周撞车一起生效，不做「哪条链路更值得重排」的分叉——同一份召回在哪个入口都该是同一个顺序。

3. **生效条件 = 开关（默认开）× 当前 Embedding 模型为 Qwen3-Embedding-8B，两条判定单源。**
   键 `secondBrainRerank` 默认 `true`；AI 面板 Embedding 组第三行「启用重排」的 `visibleWhen` 与运行期 `rerankActive()` **共用 core `isQwen3Embedding8b`**。于是「行隐藏即不生效」——用户把 Embedding 模型换成 bge-m3/4B 之后，残留的开关值不再起作用，不存在「看不见的开关还在偷偷改顺序」的暗态。换模型仍需整库重建（ADR-0182），重排只是重建后自动跟上的增强档。

4. **任一失败 → 静默回退余弦序 + `console.warn`（用户拍板）。**
   模型未装、非 2xx、响应无 logprobs、单对超时、整轮预算用尽——一律按重排前的顺序返回，不抛错、**不触发 `search()` 的文本降级**。理由：重排是增强层，失败只该损失增强，不该让用户从「向量检索」掉到「文本检索」；文本降级保留给向量链路本身的故障（ADR-0185 决策 3 的口径不变）。
   同理**不做 yes/no 文本二值降级**：二值分只有 0/1 两档，并列全按余弦序排（等于没重排），还会把 ADR-0185 刚统一掉的「两把尺」请回来。
   **例外（issue 428/ADR-0187 补）**：调用方**取消**（`AbortError`）不走回退——直抛给面板静默收口。此时回填余弦序正好会盖掉新查询的列表，与「只查最新」直接冲突。

5. **预算 6s、单对超时取 `min(20s, 剩余预算)`、串行逐对。**
   嵌入 + 全扫 + 重排共享检索级 10s（`SEARCH_TIMEOUT_MS`）。单对超时若恒为 20s，一次挂起就能让整轮跑出 20s+ 把交互式检索拖过上限，故按剩余预算收紧。串行而非并发：GPU 单实例下并发不缩短总时长（只会让每条都变慢），还会让「整轮预算」失去意义。任一对失败即整轮失败——**要么整体重排、要么维持余弦序**，不做半重排（半重排会让同一列表里混着两种排序口径，名次无法解释）。

6. **上下文与文本上限显式钉死：`num_ctx 2048`、查询 1000 字、候选段 600 字。**
   - `num_ctx 2048`：模型自带默认 40200，会让 4B 占 10.1GB 显存（无法与嵌入共驻），必须显式压；2048 档实测 3.86GB。
   - 查询截 1000 字：交互式查询（面板当前行 ≈300 字、对话提问）与每周撞车（`WEEKLY_QUERY_MAX_CHARS` 1000）本就在限内；只有**自动关联的全文查询**（上限 8000 字，ticket 118）会被截到标题 + 开篇。**召回侧仍走全文**——ticket 118 的口径不动，重排看的是笔记开篇与候选的贴合度（这也更贴近交叉编码器的训练分布：短查询 × 短文档）。
   - 候选段截 600 字：切块上限 256 字（`CHUNK_SIZE`），首块含标题、另有极少数无空白长段，截断只伤这些边角，换的是 prompt 不超上下文。
   - 条数上限 `RERANK_MAX_DOCS` = **50**（=「参考结果数 TopK」「对话参考结果数」两行的设置上限，`panel.ts` number 行 min 1 max 50）：任何合法 TopK 下**整列都吃重排**、显示与名次同尺，不会出现「已重排头部 + 只有余弦分的尾部」两段混排（初版 24 会在用户把 TopK 调到 25–50 时复现这个观感，正是用户原始投诉的形态）。**该不变式由 `tests/secondbrain/panel-settings-rows.test.ts` 钉住**（先断言两行的 `max` 字段确实是数字，再断言 `max ≤ RERANK_MAX_DOCS`——`?? 0` 式的写法在本 review 收口里已删，防「max 缺失即恒真」的空转断言）。
     **超长列表（> 50 条）整轮不重排（二轮 review 收口）**：初版结构是「头部 50 重排 + 尾部保持余弦序接在其后」，但把上限提到 50 之后仍有超长列表的路径——**自动关联候选池 = `max(TopK × 3, 24)`，它的 TopK 上限同为 50，故池可达 150**，那条路径会长期停在半重排状态：名次口径两段混排（违反决策 5 的不变量），且那些链路自己会按 score 重排/取 max，重排每篇白付 ~1.7s GPU。故 `applyRerank` 第二条早退为 `if (hits.length > RERANK_MAX_DOCS) return hits;`——**要么整体重排、要么整体不重排**，尾部保余弦序的分段结构退役（`applyRerank` 里 `hits.slice(RERANK_MAX_DOCS)` 的尾部拼接已删）。代价：> 50 条的调用方（只有后台链路）不再获得重排增益；面板三处 TopK 恒 ≤ 50，不受影响。

7. **模型档位默认 4B；模型名可由用户覆盖（issue 429 修订）。**
   默认仍是 `dengcao/Qwen3-Reranker-4B:Q4_K_M`（`RERANK_MODEL` 常量），但运行期经 `resolvedRerankModel()` 解析：设置键 `secondBrainRerankModel` 非空即以它为准（AI 面板「重排模型」行的「获取模型」写入），留空回落常量。换更大显存的机器、或想试别的社区转换版，不必改代码重构建——**改完下一次检索即生效**（重排是纯换序层，不参与向量入库，无重建语义）。新键默认 `''`（= 用内置默认）。

## 后果

- 参考面板 / 对话的排序质量在「库里有真关联」时提升明显（实测「松果体」查询把「褪黑素」从余弦 0.602 提到重排 0.916，其余候选一步沉到 ≤0.008）；库内无真关联时重排只是把噪声换个顺序，不产生误链（候选集合与阈值判定都没变）。
- 每次检索多付 ~1s（暖态），冷启动首对多付 ~3s 载入；两者都在 10s 检索级上限内，且失败即回退，不新增用户可见的错误路径。
- 面板列表的百分比**与名次同尺**（issue 429 修订）：重排过的条目另记 `hit.rerankScore`，参考面板的百分比优先显示它（未重排/回退的条目回落余弦）——用户报的「没有按照相关度由高到低去排序」实为两把尺的观感，显示层收口后消失。**阈值判定仍只读 `hit.score`（余弦）**，本 ADR 决策 1 的单尺原则不破；对话面板的百分比仍按余弦（用户明确「只在灵感参考界面」，本轮不动）。
  **显示尺跨端单源（二轮 review 收口）**：`relevancePct(hit) = round((hit.rerankScore ?? hit.score) × 100)` 由 `vector-store` 导出，桌面参考面板与移动端参考列表共用同一函数——移动端 `searchMobile` 走的也是 `vectorSearch`（同一份重排名次），列表百分比与名次同尺是**同一个「灵感参考」功能的两端**，尺不能各用各的（本收口前移动端仍显示余弦，与它自己的名次对不上）。
  注意 > 50 条整轮不重排之后，「混尺」在任何配置下都只剩「整轮回退」（此时全列回落余弦，仍是单一尺）这一种来源。
- `secondBrainRerank` 是新增键，随 `DEFAULT_SETTINGS` 一起落盘（默认 true）；`secondBrainRerankModel` 同批新增（默认 `''` = 内置默认）；旧库、旧设置无迁移动作。
- **顺序不敏感的三条链路**：建链管线（`link-agent/pipeline.ts` 收到候选后自己按 score 重排）、挂载建议（`mount-suggest.ts` 取 maxScore）、每周撞车（`weekly.ts` 取 max）都不看顺序 → 重排对它们的产出本来就零影响。**二轮 review 收口后连成本也不付了**：建链候选池 `max(TopK×3, 24)` 在 TopK > 17 时就是 > 50 条 → 走「超长列表整轮不重排」早退（初版口径下这些调用每篇白付 ~1.7s GPU）；每周撞车（TopK 10）仍在限内、照常重排（它也不看顺序，只是没到跳过线）。
- **面板超时后重排仍在后台跑完**：检索级 10s 是 `search()` 的 `Promise.race`（不 abort 底层链路），故极端冷启动下用户已拿到文本降级结果、重排链仍可能续跑 ≤6s（占用 Ollama）。代价有界、不影响用户可见结果，暂不为它做 AbortSignal 穿透。（**issue 428 起**：面板换新查询 / 关面板会真中断重排链——取消通道一路透穿到 `rerankOne`；只有「超时」这条失败路径仍不中断底层，见 ADR-0187。）
