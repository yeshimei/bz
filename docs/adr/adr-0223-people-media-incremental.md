# ADR-0223 · 脸谱媒体导出的增量口径（存在判定先行 · 欠账永久化阻断）

日期：2026-09-30 · 状态：已采纳（档 B「索引驱动」与决策 3 已于同日真跑实测后修订撤回，见文末「修订」）·
关联：ADR-0196（画脸谱任务链）、ADR-0197（聊天仓唯一写者）、ADR-0219（Windows 原子写）、
issue 515（媒体无欠账跳过预处理段）、issue 520

## 背景

「画脸谱」每次补画都被用户感知为「全量导出媒体、全量派生，特别慢」。查证后是三层原因叠加：

1. **工具侧存在判定顺序错**（`bz_prep.py`）：`do_image` / `do_video` 先 `read_bytes()` +
   `decode_dat()`（AES 多密钥轮试）**然后**才判 `target.exists()`——已导出的文件每轮都要完整读盘
   和解密一遍，算完直接丢。四类媒体里错的两类正是体量最大的两类（1631 张图 936MB + 全部视频）；
   `do_file`、derive 段、语音段都是「判定在前」，是对的。
2. **三次全量目录遍历**：段 1 `attach_dir.rglob('*')`、段 2 与段 3 各 `img_root.rglob('*')` 一遍。
3. **欠账永久化**：插件侧 `pendingMediaCounts` 的欠账口径是「媒体消息且 `text` 为空」。图片描述
   失败的图 `text` 恒空 → 永远判有欠账 → 每次补画都重起 prep 进程，把 1、2 重走一遍。

issue 515 已在**插件侧**挡掉「无欠账」这条路径（不起进程），但「确实有欠账时」的那一次仍是全量
白读；且只要有一张图描述失败，就永久落回这条昂贵路径。

## 决策

1. **存在判定先行（档 A）**：`do_image` / `do_video` 先探测产物存在再决定是否读源字节。
   `do_image` 的目标名取决于解密后才知道的扩展名（`jpg/gif/png/bin`）→ 按 `IMAGE_EXTS` 顺序探测，
   命中即 `skip`（`.bin` 命中仍走 `try_wxgf` 补解码，语义不回退）；`do_video` 目标名与 ext 无关，
   一次判定即可。**已导出文件的代价从「读全字节 + AES 轮试」降为一次名字查。**
   （探测**原语**同日修订为「目标目录 listdir 名字集合」，见文末修订。本条的价值不变，且实测
   远大于当初估算——它是本 ADR 唯一真正有效、且效果成倍的一条。）
2. **【已撤回，见文末修订】~~索引驱动增量（档 B）~~**：原定段 1 不再每轮全量 `rglob` attach 目录，
   改用 `<数据根>/<联系人>/.bz-face/media-index.json`——存各月份子目录 mtime + `hex → 月/文件名`
   映射；mtime 未变的月份读缓存，变了的月份只重扫那一个目录。**实测该扫描从来不是瓶颈**
   （3228 文件 256ms，而建索引冷启动 372ms 比它更慢），不值得一个磁盘缓存与一套指纹失效语义。
3. **【已撤回，且从未实施】~~派生与关联段复用产物清单~~**：原定段 2 derive 与段 3 map 不再各自
   `rglob` 一遍 `image/`、共用同一份按月份 mtime 失效的产物清单。实现里两者一直是各自 `rglob`
   （从未改过）；实测这两遍遍历各 ≈100ms 量级，同样够不上瓶颈。撤回理由同决策 2。
4. **保留「全量源文件过一遍」的结构，而非纯消息流驱动**：`thumb/`（微信自带缩略图）与未挂消息的
   附件不进消息流，纯消息驱动会漏。档 A 把「读盘解密」消掉之后，遍历本身（3228 文件 ≈256ms）
   就够便宜了，直接留全量遍历最省事、也最少一层状态。语音段沿用既有水位口径（本就按 `voice.json`
   跳过），不动。
5. **【已随决策 2 失效】~~索引只决定「要不要重扫」，不决定「扫到之后怎么判」~~**：撤回索引后已无
   缓存可失效，本条自动作废。**正确性只押在「产物存在与否」上**（决策 1），比原方案少一层推理。
6. **欠账永久化阻断**：任何「确定性失败、永不重试」的媒体项（如 ADR-0224 的敏感标注）必须同时从
   `pendingMediaCounts` 的口径里排除，否则每轮补画都会重新触发一次全库扫描。**这条是硬约束：
   新增任何终态跳过标记时，欠账口径必须同步。**

## 备选

- **只在插件侧加缓存、不改工具**：插件能拦「完全无欠账」，拦不住「部分欠账」时工具侧的全量白读；
  根因在工具侧，改在插件侧是错层。
- **纯消息流驱动（照搬语音段）**：语义最正，但漏 `thumb/` 与未挂消息的附件；且 `img` 字段到源文件
  的映射仍需一次目录遍历，省不掉首次成本。
- **按「上次水位时间戳」裁剪**：微信可能把补下载的历史文件写进旧月份目录，按时间戳裁剪会漏。
- **把 attach 目录整体当可删缓存**：不可逆，且那是微信自己的数据。

## 后果

- 媒体无变化的第二轮 prep：媒体段近乎瞬时（全在内存名字集合里查），日志里 `skip` 计数远大于
  `done`，与「已经导出过」的事实一致。
- 代价：**无新增磁盘产物**（索引撤回后，数据根不多任何文件）。
- 与 ADR-0197 不冲突：**权威仍是聊天仓**；判定只看产物在不在。

## 修订（2026-09-30，用真实数据真跑一遍后）

起因：issue 520 落地后按要求拿真实数据（数据根 `E:\Obsidian\微信脸谱数据\export_full`）真跑工具段
复核，量出三组与原估算相反的数字。

**一、档 A 的价值被严重低估——它才是「特别慢」的全部。** 原估算只量了 `read_bytes`（大琳 3228 条
≈681ms），**漏掉了 `decode_dat` 的 AES 多密钥轮试**。端到端实测（「大琳」：1595 图 + 1627 缩略 +
1289 语音全部已就绪、零写入）：

| 版本 | 每轮耗时（3 次） | 中位 |
|---|---|---|
| 旧版（存在判定在后） | 131.4s / 129.5s / 130.9s | **≈131 s** |
| 档 A 落地后 | 4.4s / 4.6s / 4.4s | **≈4.4 s** |

即 **≈30×、每轮省 ≈126 秒**。4.4s 里 Python 启动 ≈0.25s、DB 装载 ≈0.02s、全量遍历 ≈0.26s，
其余主要是 4517 条存在判定与协议行 I/O。

**二、档 A 第一版的原语（逐条 8×`stat`）选错了，比旧版还慢。** `IMAGE_EXTS` 有 8 个候选，
逐条试 = 3228 × 8 = 2.6 万次 `stat`；Windows 单次 `stat` ≈30µs → ≈850ms，**高于旧版读全部源字节的
681ms**。改为「每个目标目录 `listdir` 一次建成文件名集合，之后按 `IMAGE_EXTS` 顺序做集合成员查」：

| 联系人 | 源文件 | 旧版 read_bytes | 逐条 8×stat（第一版） | listdir 集合（现行） |
|---|---|---|---|---|
| 大琳 | 3228 | 681 ms | **849 ms** | **14.6 ms** |
| 周宥希 | 1667 | 412 ms | 366 ms | 8.7 ms |
| 丘羽 | 645 | 171 ms | 101 ms | 3.7 ms |

两种口径**逐条等价**已交叉验证（6 个联系人、5556 条、0 差异）。验证过程另抓到一个坑：`listdir`
顺序随机，naive 实现「取第一个命中的扩展名」会把 `bin` 报在 `jpg` 前面——命中数一样但**语义不等价**
（`.bin` 命中要触发 `try_wxgf` 补解码）。故现行实现**必须**按 `IMAGE_EXTS` 顺序扫。

**三、档 B 撤回。** 同一批真实数据上量：全量 `rglob` 扫 3228 个文件只要 **256ms**；建索引冷启动
**372ms（比它要取代的扫描还慢）**、热态 45ms，热态只省 ≈200ms。相对 131s 的真瓶颈与 4.4s 的现状，
这 200ms 换不来一个磁盘缓存加一套指纹/版本失效语义。**决策 2 撤回；决策 3 本就未实施，一并撤回。**

**四、判定范围**：`do_image` / `do_video` 走 `TargetIndex`；`do_file`（附件）与语音段保持一次
`stat` 原样——不在档 A 修复范围，量级也摊不出来。

**五、顺带查到、本 ADR 不处理**：媒体段的 `[bz-p]` 进度是**逐条打点**（大琳一轮 6221 行 / 238KB，
而不同 `pct` 只有 101 个），map 段早已按 pct 去重。独立问题，另开票。
