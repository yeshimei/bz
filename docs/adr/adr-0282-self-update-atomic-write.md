# ADR-0282 · 自更新落盘改为原子替换 + 失败回滚

日期：2026-11-01 · 状态：已采纳（同日实现）

## 背景

1. 用户 2026-11-01 反馈「更新插件总觉得不是很稳定」。
2. 排查后确认最危险的一处不在网络，而在**落盘方式**：`checkSelfUpdate` 此前是三行
   `adapter.write`，直接往正式文件里写。`main.js` 有 2.8 MB，`adapter.write` 的语义是
   「打开正本 → 截断 → 写入」，中间任何一拍出事（断电、Obsidian 崩溃、磁盘写满、
   安全软件临时锁文件、OneDrive 之类的同步盘截断）都会在磁盘上留下**半截 main.js**。
3. 这一处特别致命，因为**自更新的代码本身就在被覆盖的那个 main.js 里**。插件加载失败
   的现场是「没有任何代码能跑」——`downloads/.backup/<旧版本>/` 明明躺着完好的旧三件套，
   却没有东西能把它们拷回去。用户的表现是 Obsidian 报插件加载失败，除了手动进文件夹，
   没有第二条路。
4. 顺带两处同源问题：写之前不知道磁盘还剩多少（满了要写到一半才发现）；
   三件套逐个写，第二件失败会留下「新 JS + 旧 CSS」这种半装。

## 决策

### 1. 原子替换：写临时件 → 读回核对 → `rename` 覆盖

`writePluginFileAtomic(app, name, text)`：

1. 写到 `<文件>.bz-tmp`（与正本同目录，保证同盘）；
2. 用 `fs.readFileSync` 读回，与待写内容逐字比对；
3. 一致才 `fs.renameSync(tmp, 正本)`——Node 在 Windows 走 `MoveFileEx(REPLACE_EXISTING)`、
   POSIX 就是 `rename(2)`，都是**原子**的：要么旧内容，要么完整新内容，没有第三种。

不用 `adapter.rename` 的三段式（像 `encrypt/data.ts` 那样先挪 `.bak` 再搬入）：那套在
「挪走旧件」与「搬入新件」之间存在一个 main.js 不存在的窗口，对插件本体来说同样致命。
桌面端拿得到 Node fs，直接用真正的原子 rename。

**拿不到 Node fs 时退回 `adapter.write` 直写**（非桌面端 / 异常运行时）。那是改动前的
既有行为，不是新引入的风险；备份与下面的回滚仍然有效。

### 2. 半装回滚：任何一件写失败，已替换的按备份退回

三件套按 `main.js → styles.css → manifest.json` 顺序替换（manifest 最后：它决定版本号，
写早了会出现「版本已是新版、代码还是旧的」）。任一环失败：

- `replaced === 0`（第一件就没写成，正本一字未动）→ 只报错，不动任何文件；
- 否则调 `restoreFromBackup(app, localVer)` 用本次备份把三件套整体退回，并作废
  `bz-selfupdate:pending`。回滚本身也走原子写。

错误消息里带结论：`（已自动回滚到 vX）` 或 `（回滚失败，备份在 downloads/.backup/X）`。

### 3. 写前预检：空间不够在动手之前就退出

`preflightSpace` 在备份**之前**跑，用 `fs.statfsSync`（Node 18.15+，拿不到就跳过）核
可用空间，低于 `MIN_FREE_BYTES`（16 MB：三件套约 3 MB + 一份备份约 3 MB，留一倍余量）
直接抛「磁盘空间不足（剩 X MB…）」。目的不是防崩（原子写已经兜住了），是别让用户等
三分钟才看到一句失败。

## 代价

- 每次更新多一次读回（2.8 MB 字符串比对，毫秒级）与一次 rename。
- `rename` 要求临时件与正本同盘：两者都在插件目录内，天然满足。
- 崩溃在「已替换 main.js、尚未替换 styles.css」之间（不是异常，是断电）仍然会留下
  新 JS + 旧 CSS。这种场景代码没机会跑，靠的是备份 + 人工恢复，不在本条范围内。

## 未做（用户只采纳了这一条）

备份目录仍**没有回滚入口**（面板按钮 / 插件加载失败后的自动恢复都没做），
备份也没有清理策略。`restoreFromBackup` 已经是现成的底座，做 UI 时直接复用。
