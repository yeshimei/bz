# ADR-0171：日记本打开「先面板后内容」——首帧让位读盘与整墙渲染

- 日期：2026-09-19
- 状态：已采纳
- 相关：issue 383；issue 381 / ADR-0170（墙数据启动预热 + 缓存）、ADR-0003（懒加载）

## 背景

`show()` 本就同步 `display=flex`，面板不留白。但 issue 381 引入「开墙吃缓存」后出现了新路径：
缓存命中时 `loadWallEntries` 立即 resolve，`show() → loadAndRender` 整条链在微任务里一口气跑到
`renderAll`，浏览器首帧被「读盘 + 整墙 DOM 构建」堵住 → 观感「点了没反应，然后整墙突然出现」，
用户以为卡了。用户拍板：**打开日记本必须先给面板**。

## 决策

1. **让位首帧**（`afterPaint()`）：`loadAndRender` 在 `showSkeleton()` 之后 `await` 一拍
   「rAF → setTimeout(0)」——面板（display=flex）与骨架先上屏（浏览器完成一次绘制），
   再放行读盘与整墙渲染。范式对齐 `prewarmDiary` 的「rAF + setTimeout 到空闲」。
2. **插一处覆盖全部调用点**：`afterPaint` 只在 `loadAndRender` 一处；开墙 / 刷新 / 写后回刷 /
   重试 / 加密合并后各调用点天然继承。除开墙外路径本就在面板可见时跑，各多一帧延迟（可忽略）。
3. **隐藏窗口 / 无 rAF 环境直接 `setTimeout(0)`**：后台标签页 rAF 不触发，等它会把刷新卡住。
4. **数据层零改动**：只改 UI 侧时机；`loadWallEntries` / 缓存 / 失效（ADR-0170）语义原样。
5. **不加人为 loading 下限**：让位只等一帧（~16ms），不是表演式最小 loading 时长。

## 后果

- 冷开与缓存命中开：`openManager` 返回瞬间面板 + 骨架已在屏上，内容随后到达（骨架退场）。
- 重开旧墙：`showSkeleton` 对已有内容的墙跳过（旧内容留场）→ 首帧即旧内容，无骨架闪烁，
  刷新体验不变（新语义下让位后照常重读重渲染）。
- 刷新 / 回刷路径：多一帧延迟，语义不变（「读盘必发生」类断言不受影响，只是晚一帧）。
- 测试：既有 `waitFor` 轮询天然兼容；新增 2 例钉住「`openManager` 返回时骨架在位、内容未到」
  这条新契约（冷开 + 缓存命中各一）。

## 被否决的方案

- **`show()` 拆两段（先建面板，再异步补数据）**：现有结构已是「show 同步建面板 +
  loadAndRender fire-and-forget」，缺的只是首帧让位；拆两段是伪需求、徒增复杂度。
- **人为延时（如 200ms）让骨架可见**：无谓拖慢真实加载；骨架只是让位一帧的副产品，不是表演。
- **数据分片 / 渐进渲染（先文字后媒体）**：改动面大（解析、渲染、排序全动），收益不确定；
  首帧让位已解「点了没反应」。
