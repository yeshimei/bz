# ADR-0225 · 图片不可描述两类终态：导出那轮落 `media_fail.json`，损坏 / 缺失分开标

日期：2026-09-30 · 状态：已采纳 · 关联：ADR-0223（欠账口径必须同步、prep 增量）、
ADR-0224（敏感跳过，`descSkip` 首例）、ADR-0197（聊天仓唯一写者）、ADR-0196（任务链）、
issue 521

## 背景

用户实测（承 520）：「20 张待描述，我点击开始生成，直接全部跳过，又开始生成其人。」保库解锁后逐条
核对，全库「待描述」合计 **304 张，100% 派生档缺失**——一张能描述的都没有。分两类：

- **坏档 84 张**：源图 `image/<月>/<名>.jpg` 在，但 Pillow 打不开（`UnidentifiedImageError` /
  `broken data stream`）；
- **缺失 214 张**：连 `image/` 源文件都没有，只剩微信缩略图 `thumb/`；
- 另有 6 张源图正常但 `derive` 段没跑到。

根因有两处，都在 prep 侧「不落账」：

1. **两类不可用都只在内存里走了一遭**。缺失：`bz_prep.py` 段 3（map）比对「消息引用的图 ↔ 磁盘解码
   产物」时，`rel` 为空便静默 `continue`，不写进任何产物表 → 插件的 `img` 保持 chat 原始值（无扩展
   名），描述段拿它拼 `desc/<月>/<hex>` 永远读不到档。坏档：段 2（derive）对源图 `Image.open` 抛异常
   时只累加 `derive["fail"]` 计数器，产物表里不留条目。
2. **描述段把「读不动派生档」当成了「本批没事做」**。`runDescribeStage` 批循环里 `descDataUrlOf`
   全 null → `led.doneBatches++ ; continue`（本意是「不烧调用、计完成跳过」）。结果整段**零调用**走
   完、账本显示 17/17 批完成，而聊天仓里那 20 张 `text` 依旧为空 → 「欠账口径说 20 张」与「批完成口径
   说全完成」互相矛盾，下一轮仍是 20 张，**永远不收敛**。

附带副作用：描述段跳过 ≠ 整链停，其后**其人 / 相交 / 纪事 / 档案提炼固定 4 次调用**照跑。用户那次
只有 1 条新增素材，5 次调用纯白烧。

用户拍板（2026-09-30）：

1. **坏档补坏档的标注、缺失补缺失的标注**（两类分开）；
2. **这件事在第一次导出媒体的时候就该做**——不在补画时才补救，不给后续留遗留问题；
3. **描述段零进展时加短路 + 明确告知**，不再把画像段跑一遍。

## 决策

### 1. prep 侧新增权威旁路表 `media_fail.json`（在导出那轮落定）

`bz_prep.py` 段 3（map）末尾**一次性**写出 `<数据根>/<联系人>/media_fail.json`，数组，元素：

```json
{"file": "<月>/<名>", "reason": "missing" | "broken", "ct": 1754394429, "sid": 2952}
```

- `missing`：消息引用了图片，但磁盘上没有可消费的解码产物（源图没导出 / `.bin` 没解出来）。
  `file` 取 chat 原值（可能无扩展名）；
- `broken`：磁盘上有产物，但本轮 derive 段打不开（段 2 把失败项记进 `derive_failed` 集合，段 3 比对
  时归类）。`file` 取产物名；
- 两者都同时带 `ct` / `sid`，与 `image_map.json` 同口径——插件按 `sid` 优先、`img` 精确、`ct` 兜底
  三级匹配。

**写表守卫（关键）**：`--limit > 0`（调试半轮）时**不写该表**。半轮结果会把「这一轮没轮到」误判成
`missing`，而 `missing` 是不可逆终态——宁可表缺失（= 无权威、插件不动标注）也不能写错。**表缺失 =
无权威**；**空表 = 权威地表示全部可消费**（于是插件清掉旧的 `broken`/`missing` 标注）。

### 2. 插件侧两类终态标注，与敏感并列

`StoreMsg.descSkip` 从单值 `'sensitive'` 扩为三值 `DescSkip = 'sensitive' | 'broken' | 'missing'`
（类型层面仍是可选派生字段，**不动** `PeopleSafeRecord.version`，与 ADR-0224 决策 6 同口径）。
`isDescSkipped` 语义变为「**是否已是终态跳过**」（三种都算），新增 `descSkipOf` 做归一（未知取值当未
标注）。

- **不算欠账**（`pendingMediaCounts`）、不切批、不进 describe 段 `refs`——待描述归零，不再每轮重扫
  （落实 ADR-0223 决策 6）；
- 图片页签格子上分别显示 `源图损坏` / `源图缺失`（与 `敏感` 并列），**不给解除入口**——坏档 / 缺失
  是磁盘事实而非启发式判定，没有误伤也就不存在「重试」的意义。title 说明「重新导出媒体后会自动重试」；
- **表即权威（自愈）**：并仓时把当前标着 `broken` / `missing`、但**不在最新表里**的图**清掉标注**
  ——用户重导媒体、源图修好后，下一轮 prep 自动把它放回可描述队列，不需要手工撤。落地实现是
  `applyMediaFailToMsgs(msgs, items)`：只处理 `type===3`、`text===''`、且非 `sensitive` 的消息；
  `items` 为 `null`（表缺失）时整体不调用 = 不动标注。

**先并 `image_map.json`、后并 `media_fail.json`（次序要紧）**：`image_map.json` 会把 chat 的
`img`（无扩展名）改写为产物相对路径（带扩展名），而 `media_fail.json` 的 `broken` 条目 `file` 用的是
**产物名**。次序反了，两类都对不上号。这是实现期暴露的次序要求，与 ADR-0224 决策 5（标注必须先于
`applyImageDescToMsgs`）同源。

### 3. 描述段「有欠账、零可读」直接收尾（用户拍板）

`runDescribeStage` 新增终态返回 `'unreadable'`：有欠账（`pendingCount > 0`）但整段批循环**零可读**
（`readRefs === 0`）。`runJob` 收到即收尾为 `done`、**不进画像段**，并明确告知：

> 「丘羽」本次没有可提炼的内容：20 张图片的源图损坏或缺失，无法生成描述

**判据收窄的理由**：决策 2 落地后死欠账已不再是欠账，**「有欠账、零可读」只剩两种成因**——本轮刚
导入、派生还没跑起来，或磁盘 / 数据根临时掉线。两种都该停下来说清楚，而不是继续烧 4 次成文调用。

## 备选

- **插件侧自行探测源图**（描述段读不到档时现场 `stat`/`Image.open` 分类）：把媒体知识塞进插件，且
  每轮都要试读磁盘，慢且与工具侧结论可能打架。选工具侧在导出那轮一次落定（用户明确要求「就该在这
  做」）。
- **两类合成一个 `'unusable'` 标注**：少一个取值，但用户要求「坏档补坏档、缺失补缺失」——两类成因不
  同（一个能修、一个要补导出），分开标才好指导用户动作。
- **给 `broken`/`missing` 做「解除」按钮**：只会把用户送进「解除 → 又跳过 → 再标注」的空转；撤销
  语义交给 `media_fail.json` 权威性（重导自动清）。
- **描述段零可读时静默收尾、不出提示**：用户正因「神秘数字」在追问，必须明确告知张数与成因。
- **重试 / 修复坏档本身**：源图是微信备份里就坏的，插件无从修。**不做。**

## 后果

- 死欠账归零：`pendingMediaCounts` 对全库收敛，「待描述」不再含补不上的图，补画谱不再每轮空转。
- 用户可见两种新角标（源图损坏 / 源图缺失），把 304 这个「神秘数字」拆成可解释的成因。
- 重导媒体后自愈：修好源图 → 下一轮 `prep` 表里不再有该条 → 下轮并仓清标注 → 回可描述队列。
- 描述段零进展时零画像调用（省下固定 4 次成文调用）+ 明确提示。
- 诚实边界：分类依赖工具侧 `Image.open` 结果。源图「能打开但画质差」不在此列（那仍会被正常描述，
  只是描述质量另说）；表只在**完整轮**（无 `--limit`）写，调试轮的自愈被刻意关掉。
