# ADR-0235 · 工具坞：外部工具用「声明文件」自描述，参数值住工具侧

日期：2026-10-04 · 状态：已采纳 · 关联：issue 461（四行协议抽核心层）、ADR-0106（原型评审壳范式）、
ADR-0218（重进程串行化）、ADR-0219（原子写）、规格 `.scratch/dock/spec.md`（D1–D15）

## 背景

工具坞（dock 域）第一版按「工具自描述 = `<cmd> --manifest` 子命令吐一行 JSON、bz 缓存它」
落地。实现完、灌进真实 vault、接上首个外部脚本（iamtxt 每日签到）之后，用户点破了三处根本不对：

1. **数据放反了**。工具的名字、描述、参数定义、节奏，本来全是**工具自己的事**，却被拆成两半：
   bz 的登记表里又存了一份 `name` / `note` / `trigger`，`--manifest` 里再声明一遍。同一件事两个写者、
   两处会漂。用户的原话是「什么标题、描述、参数等等……不需要填写表单，设置数据放到外部脚本侧，
   bz 相关的数据才放到仓库中」。

2. **参数值会丢**。用户填的 Cookie 只活在 `ui.ts` 的 `formValues`（内存 `Map`）里，重启即蒸发 ——
   而它恰恰是**每次运行都必须有**的东西。用户得反复重填，等于这个工具根本不可用。

3. **信任顺序是蒙眼签字**。原设计里「信任此命令」必须先于「看见命令是什么」：不先信任，就跑不了
   `--manifest`，也就拿不到要信任的那条命令。这是 D5 信任边界被自己的实现绕过去了。

另有一处是在落地过程中被同一个方向的追问带出来的：**注册时「自动化 / 手动」要用户填**。可这个值
本来就从工具声明的节奏（`schedule`）唯一地推导出来，让人再填一次只是多一个能填错的地方。

## 决策

### 1. 声明文件 `dock.json` 住工具目录，bz「读文件」导入，不执行任何东西

工具目录下放一个手写声明文件 `dock.json`（文件名是契约的一部分），内含标题 / 描述 / 图标 /
分组 / 参数定义 / 节奏 / **启动命令**。bz 的「导入声明」动作就是**读这个文件**：

- 读文件不执行任何东西 —— 于是「先看清它会跑什么，再决定信不信任」这个顺序才成立（修回 D5）。
- **bz 不缓存声明**。缓存会过期，而过期本身就是缺陷来源：脚本改了声明、vault 里那份旧缓存还在，
  面板就照着旧缓存渲染出早就删掉的参数（落地时真发生过：`iamtxt-signin` 的缓存里还是第一版被
  用户否掉的 4 个参数 `site`/`cookie`/`signinUrl`/`timeoutSec`）。读文件很便宜，直接读。
- 声明文件的 `id` 决定记录文件名；路径解析（`resolveRun`）里 `cwd` 缺省 = 声明文件所在目录，
  `shell` 缺省由启动命令的扩展名（`.cmd`/`.bat`）判定。

### 2. 参数值住工具目录下的约定文件 `dock.settings.json`

用户填的参数**值**（Cookie 这类凭据）写进声明文件同目录的 `dock.settings.json`：

- 它是 **bz 写、工具读**（实际工具不必读 —— 运行前 bz 已把值经 `--key=value` 下发；这个文件是 bz
  的账本，只是住得离工具近）。
- 好处一：**不在 vault 的 `data.json` 里**，因而**不跟着 vault 同步、不进 git、不落运行记录**。
- 好处二：**跨重启存活**。这是修 2 号问题的落点。
- 写入走 tmp + rename 原子替换，带版本号 `DOCK_SETTINGS_VERSION`；版本/工具 id 对不上一律当「没有值」，
  不猜。

### 3. 登记表收缩到「bz 相关的数据」

`data.json` 的 `dockTools` 段自此**只留** bz 自己必须知道的东西：

```jsonc
{ "id": "iamtxt-signin", "path": "E:/Obsidian/dock-tools/daily-signin/dock.json",
  "enabled": true, "trustedAt": "...", "trustedRun": "<签名>" }
```

`cmd` / `args` / `cwd` / `shell` / `name` / `note` / `trigger` 全部从登记表移除 —— 它们要么已进
声明文件（`run` 段），要么可由声明派生（`trigger`）。`parseToolEntry` 对遗留字段**直接忽略**，
不做迁移（老登记项重新导入一次即可）。

### 4. 「自动化 / 手动」由节奏派生，不再让用户填

`triggerOf(schedule)` 是唯一口径：声明了 `daily` / `weekly` / `interval` → `auto`，
否则 → `manual`。UI 的两分区、KPI 的自动化口径全部消费它，**不在渲染层另算一套**。

### 5. D5 信任边界在「命令移进声明文件」之后原样保留

命令落进声明文件，意味着**改文件就能改执行的东西** —— 这正是 D5 要防的。对策是把信任从
「信任这条登记」升级为「信任这条**命令的签名**」：

- 登记项存 `trustedRun`（`runSignature(run)` = `cmd\0shell\0args.join`）。
- 视图层算 `trustStale` = 已信任 且 当前声明里的签名 ≠ 信任时的签名。
- `canStart` 含 `!trustStale`；卡面/详情给出「命令已变，待重新确认」标签；点运行或重读声明时，
  命中 `trustStale` 就弹出**展示新命令**的确认框（`applyTrust`）。

结论：**声明文件能改界面（名字/描述/参数），改不了已在跑的这条命令 —— 除非用户再看一眼并重新确认。**

## 明确不做

- **`bz-dock-run-<工具id>` 命令（原 spec §1 的命令表）缓做**。日志里没有「不打开面板就跑某个工具」
  的真实场景；快捷键诉求可以等有人真提。先在 spec 里标为未实现，不假装有。
- **D13 的「全仓 5000 条」上限缓做**。裁剪权归工具（D8/D13），bz 只检测、只提示；每工具 200 条这条
  是工具侧的事，全仓聚合上限在工具数量还是个位数时是空转。等工具多到需要它再加。
- **不迁移 knowledge / people 两个既有外部工具通道**（spec D15，本条不变）。

## 后果

- **修好了三处根本问题**：元数据单源（工具侧）、参数值跨重启存活（工具侧文件）、信任顺序正确
  （读文件不执行 → 看清再信）。
- 登记表变小，`data.json` 里与 bz 无关的东西归零 —— 换机器/分享 vault 时泄露面收窄。
- **文件从三份变四份，但「一文件一写者」不变量不变**（原 D9 的全部意义）：

  | 文件 | 唯一写者 | bz 的角色 |
  |---|---|---|
  | `data.json` → `dockTools` | **bz** | 属主 |
  | `<工具目录>/dock.json` | **工具作者** | 只读导入 |
  | `<工具目录>/dock.settings.json` | **bz** | 属主 |
  | `CONFIG/STORAGE/dock/runs/<id>.json` | **工具** | 只读、只检测 |

  没有任何一份文件被两个写者碰过。
- 代价（要认）：**声明文件与登记表可能各说各话** —— 工具作者改了 `id`，而登记项还挂着旧 `path`。
  对策是 `loadToolView` 把「声明读不到 / id 对不上」显式做成 `declError`，面板照实报错，不静默失效
  （旧设计里 `id` 错位是**静默失效不报错**的，这条是净改进）。
- 首个外部脚本（`iamtxt-signin`）需从「登记表内联 `cmd/args` + `--manifest`」迁移为「工具目录两文件 +
  登记项只留 path」。参考实现 = `E:\Obsidian\dock-tools\daily-signin\`，契约文档 = `docs/dock-tool-guide.md`。
