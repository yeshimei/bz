# ADR-0236 · 工具坞：运行记录归工具目录；bz 亲自调度自动化工具

日期：2026-10-04 · 状态：已采纳 · 关联：ADR-0235（声明文件 + 参数值住工具侧，本条的上一节）、
ADR-0218（重进程串行化：bz 队列内存化）、ADR-0219（原子写）、issue 461（四行协议抽核心层）、
规格 `.scratch/dock/spec.md`（D1/D10 修订，§14）

本条一次拍定两件事，因为它们同出一源——都在回答「一个工具的数据与节奏，到底归谁」：

1. **运行记录从 vault 挪进工具目录**（D9/D10 修订）。
2. **bz 亲自调度自动化工具**（D1 修订，推翻「dock 不参与调度」）。

---

## 决策一：运行记录归工具目录（`<工具目录>/dock.runs.json`）

### 背景

ADR-0235 把声明与参数值都搬到了工具侧，但运行记录还留在 vault 里
（`CONFIG/STORAGE/dock/runs/<id>.json`）。接上首个真脚本后这条立刻露了馅：

- **一个工具的数据被劈成两半**：声明 + 参数值在 `E:\Obsidian\dock-tools\daily-signin\`，
  运行记录却在 vault 里。搬走工具目录 ≠ 搬走这个工具。用户的原话是
  「脚本生成的数据也应该在脚本侧，而不是放到 bz 侧」。
- **绝对路径这个坑是它逼出来的**：工具进程的 `cwd` 是它自己的目录，bz 从前注入的
  `BZ_DOCK_RUNS_FILE` 是「vault 根 + vault 内相对路径」，于是记录被写进了
  `<工具目录>/CONFIG/STORAGE/dock/runs/...`，bz 在 vault 里怎么也找不到 —— 表现为
  「跑完了却没有记录」（master `90e80ed5` 用绝对路径堵过一次，但那只是治标）。

### 决策

运行记录文件名固定为 `dock.runs.json`，位置固定 = 声明文件同目录（`declaration.ts` 的
`RUNS_FILENAME` / `runsPathFor`）。于是工具目录下的三份文件同址：

| 文件 | 唯一写者 | bz 的角色 |
|---|---|---|
| `dock.json` | 工具作者（手写） | 只读导入 |
| `dock.settings.json` | **bz** | 属主 |
| `dock.runs.json` | **工具** | 只读、只检测 |

- `BZ_DOCK_RUNS_FILE` 从「vault 根 + 相对路径」改为 `runsPathFor(entry.path)`，
  **天然是绝对值**（路径从声明文件位置推出来），那条「cwd 把相对路径解析歪」的坑
  从根上消失。
- 读侧（`readRunsText`）**只有 read、没有 write** —— bz 一写就成了第二个写者（D9 不变）。
- 代价（要认）：`D10` 原意「路径由 bz 约定、物理上也统一」让位于「工具数据自包含」。
  「一文件一写者」这条不变量不受影响。

## 决策二：bz 亲自调度自动化工具（D1 修订）

### 背景

原 D1 是「dock 不参与调度」，让用户在系统任务计划程序里自己配节奏、自己写死路径、自己
处理凭据。落地后的真实体验是：**本域最重的活全推给了用户，还换不来任何好处** ——

- 漏跑没人补、失败没人重试、状态事后才知道（要跑去系统计划任务里看历史）；
- 工具得自己在 OS 任务定义里写死一份 vault 路径，跟 bz 侧再来一份，两处会漂；
- 与「工具坞是一个集中观测台」的定位直接矛盾：观测台却管不到触发。

用户拍板改口：**节奏由工具声明（`schedule`），由 bz 执行**；bz 侧还可以覆盖（改节奏、
关某个工具的自动运行）。既然已经有「补跑 / 重试 / 台账」这套东西，就不该再把它们留给用户。

### 决策

1. **判据与执行分离**。判定是零依赖纯函数（`schedule.ts`），执行是薄运行时
   （`scheduler.ts`）：
   - `effectiveSchedule(declared, override)` = 用户覆盖 ?? 作者声明（**整体替换**，不做字段级合并）。
   - `isDueToRun()` 与告警口径 `judgeDue()` **刻意分开**：`interval` 首次时前者答「跑」
     （工具刚装好就是要它开工），后者答 `unknown`（没有基线不许喊狼，告警纪律不变）。
   - `decideDue()` 从一批工具事实里挑「现在该跑的」，**保持输入顺序**（登记顺序即
     串行执行顺序），其余给出不跑的原因（`disabled` / `untrusted` / `trust-stale` /
     `no-run` / `not-auto` / `auto-off` / `params` / `paused` / `cooldown` / `running` /
     `not-due`，顺序即优先级——先判硬门槛，最后判「到点」）。
2. **四条运行时纪律**：不并行（同一时刻至多一个工具，串行队列并发 = 1）、不连坐（超时到点
   掐掉，不堵队列）、不猜（判不出就不跑）、不诈尸（插件卸载后定时器一律短路）。
3. **闸门与台账**：
   - 总闸 `dockAutoRun`（默认开，设置页「自动运行」组）；移动端恒不生效（起不了进程）。
   - 未填必填参数不跑（拿不到 Cookie 就白跑一次网络请求），每会话每工具提示一次。
   - 失败进 15 分钟冷却，连续失败 3 次**熔断暂停**，在面板手动恢复；台账（
     `dockRunState`：`lastAttemptAt` / `lastAttemptOk` / `consecutiveFailures` / `pausedAt`）
     住 bz 的 `data.json` —— **不是**工具的运行记录，那份仍归工具自己写（D8/D9）。
4. **节奏覆盖是登记项的一层**，声明仍是单源：登记项存 `scheduleOverride` 与
   `overrideDeclSig`（覆盖时记下的声明签名）。作者改了声明节奏 → `declChangedSinceOverride`
   提示「声明变了，你的覆盖可能过期了」，但不自动丢弃用户的覆盖。
5. **在场 / 离场判据改为「谁启动」**（这是 D1 修订最容易被忽略的连锁后果）：bz 亲手拉起的
   都算**在场**——无论用户点的，还是调度器按节奏自动触发的，都有实时流、都能停止。所以
   `BZ_DOCK_TRIGGER=auto|manual` 注入给工具，只为让它给记录标对 `trigger`；对 bz 而言两者
   走同一条路。

### 硬后果（要认）

**Obsidian 关着的时候不会跑。** bz 不是父进程就无从调度。这与原 D1 的「系统计划任务兜底」
正好相反，是本次改口的主要代价。将来若真需要「Obsidian 关着也要跑」，对策是**另开一个
系统计划任务的逃生口**（bz 在面板里生成一份任务定义，交给用户注册）——那是后续单独议题，
本条不做（见 spec §14「明确不做」）。

---

## 明确不做

- **不做 OS 计划任务的创建 / 注入 / 编辑**（本次不做）。三平台后端各不相同、任务定义里要
  明文落命令与路径（等于把凭据暴露面扩大）、还要跨进程互斥与漂移检测——工程量大而收益只覆盖
  「必须关着 Obsidian 也跑」这一小类工具。留作将来的逃生口。
- **不做运行中参数注入**（D3 不变，不开 stdin 管道）。
- **不做跨工具统一资源闸**（ADR-0218 决策 9 已否决同类诉求）；调度器只保证并发 = 1，
  不为「内存争抢」另造闸门。
- **不做 bz 侧的运行记录汇总副本**（D9 不变，bz 只读、只检测）。

## 后果

- 自动化工具从「用户自己在 OS 里配」变成「声明一个节奏，剩下的 bz 管」：到点跑、漏跑补、
  失败重试与熔断、台账与提醒全在面板里。
- **新增一个常驻后台任务**（`scheduler.ts`），随插件 `onLayoutReady` 起、`onunload` 停；
  移动端不起。
- 运行记录路径不再需要用户配置（值由声明文件位置推出），工具也不必再往 OS 任务里写死
  一份 vault 路径 —— 只有「离场」形态才需要。
- 设置页从两行变三行（工具 / **自动运行** / 提醒）。
- 契约文档 `docs/dock-tool-guide.md` 增补 `BZ_DOCK_TRIGGER` 环境变量，并订正运行记录路径
  一节（旧文写的是 vault 内的 `runs/<id>.json`）。
