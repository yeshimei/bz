# ADR-0279 · 本地运行时（Python / ffmpeg）自动装；「bz 依赖什么」单源清单弹窗；目录包就绪看解包标记

日期：2026-11-01 · 状态：已采纳（同日实现合入 master，issue 563）

## 背景

1. bz 有一批功能建立在**机器上的东西**之上：知识盒视频转文字要 ffmpeg + Python，脸谱录音转写要 Python，第二大脑语义检索与小橘记忆要 Ollama + 本地向量模型。Node 早就能自动装（便携版，ADR 里没有对应 ADR，实现在 `core/node-runtime-install.ts`），这一批没有。
2. 缺了之后的提示长期停在「请确认 Ollama 服务与 Embedding 模型可用」——它没说清是**没装**、**装了没启动**、还是**没拉模型**，三种情况下一步完全不同。
3. 2026-11-01 用户报三个 bug，事后看是**同一个根因**：检测屏对目录包判的是归档文件（`docStatus` 比 `.tar.gz` 的 sha256），内容屏判的是解包目录（`bundleStatus` 看解包标记）。于是「检测说已下载但仍然要下」；解包是逐文件顺序写的，`cli.js` 排在前面，解到一半断掉时脚本已在盘上，于是「下载失败后总界面仍显示已下载」。

## 决策

1. **新增 `core/dep-runtime.ts`，统一管两个本地运行时**：Python（`python-build-standalone`，3.12.16）与 ffmpeg + ffprobe（仅 Windows 自动装，macOS/Linux 交给 brew/apt）。
   - **探测顺序 = 设置里填的 → 插件内便携 → PATH**；ffmpeg 一项必须**两个入口都在**（缺 ffprobe 不算就绪，压缩后的时长远端校验会断）。
   - 装完**回写绝对路径**进 `pythonPath` / `ffmpegPath` / `ffprobePath`：这两个是外部工具包的执行环境，路径只在设置里填不好使——引导页得把它填上，脚本才能直接跑。
   - 与 Node 的取向**故意相反**：Node 是「插件内优先」（bz 自己 spawn，要版本可控），这两个是「系统优先、插件内兜底」（机器上已有的一份可能正给别的工具用，再装一份就是两个端口、两套缓存）。
2. **通道顺序实测定，不猜**：Python 走**南大镜像 → GitHub → gh-proxy**（实测 47 MB：南大 13s / 3.6 MB/s，GitHub 20.6s / 2.28 MB/s）；ffmpeg（win32）走 **BtbN GitHub → gyan.dev**（南大没有 BtbN 的归档，gyan 实测 150 KB/s 只配兜底）。
   - gh-proxy 实测 **HEAD 200 但 GET 挂在 0 字节**——曾经把它排在前面，用户看到的就是「一直转圈」。故一律排最后，并加 **45 秒无进展超时**（`STALL_MS`）：宁可判失败让用户重试，不要一条流吊着不动。
   - 三源取件顺序仍是**缓存 → 离线包 → 网络**（`core/bundle-asset` 的既有口径），下载带 sha256 校验，解包有条目数与总字节硬上限。
3. **目录包的就绪判据统一为「解包标记在不在」**（`BUNDLE_MARKER`，产出方在 `core/bundle-asset`）：标记在 = 这份目录是完整解出来的。检测屏与内容屏**必须问同一个问题**——两屏各问一个是本次三个 bug 的直接来源。
   - `toolReadyState` 同步加这一条（此前只看入口脚本在不在），三件事齐了才算 ready：脚本 + 标记 + node。
   - 文档类单文件仍看 sha256（`docStatus`），不跟着改——它确实没有解包这一步。
4. **新增 `core/deps-guide.ts`「bz 依赖什么」弹窗，一处清单三处用**：引导完成屏的「还需要装什么？」、设置 → AI → Embedding 的「装 Ollama 与向量模型」按钮、第二大脑失败态的自动弹。
   - 覆盖下载队列**搬不动也不该搬**的那几层：云端 AI 密钥、Ollama、向量模型（bge-m3 / 可选 8B）、pip 依赖（funasr + torch / faster-whisper / pycryptodome）、转写模型、豆瓣与 B 站 Cookie。
   - 清单里的 `{python}` **换成本机真实绝对路径**再渲染——引导页刚装的那份在插件目录里，用户复制走就能跑，不写「python」让他自己去找。
   - 云端密钥 / Ollama 服务 / 向量模型三行带探测，弹窗打开后补状态，**不阻塞渲染**。
5. **第二大脑失败态按探测结论说话**，不只是换一句文案：
   - 服务没起 → 「Windows 从开始菜单打开它（或命令行跑 `ollama serve`），任务栏出现羊驼图标后重试」
   - 服务在、一个模型都没有 → 「跑 `ollama pull bge-m3`（约 1.2 GB）后重试」
   - 都在还失败 → 换更准的模型或去环境自检，**这一种不弹引导**（那张表在这里帮不上忙，弹了只是打扰）
   - 前两种每次会话自动弹一次引导；「重试初始化」在这两种情况下是纯空转，不能让用户自己发现。
6. **弹窗沿用 `bz-setup-*` 皮肤**（`core/ui/components.css`）：它就是从引导页长出来的东西，另起一套皮等于同一个插件里两种长相。

## 后果

- 正面：新机器上装完 bz 就有能跑的转写与视频处理链路；第二大脑连不上时用户知道该干什么而不是只会点重试；检查页与内容页对同一项给出同一结论。
- 代价：Python 与 ffmpeg 加在一起约 155 MB（Python 45 MB / ffmpeg 109 MB），引导页多一个可选勾选项；镜像站是第三方，条目可用性由插件侧兜底（sha256 + 多通道），但南大归档过期时 Python 那条会退到 GitHub。
- 未做：macOS / Linux 不自动装 ffmpeg（引导 brew / apt）；Ollama 与向量模型**刻意不代装**——它是通用服务，机器上可能已经有一份在给别的东西用，模型要落在 Ollama 自己的目录里。
- 测试侧连带发现：`skin-pack-split-guard` 的反向守卫把探测文件写成固定名，一轮跑被打断（Ctrl+C / 超时 / 管道截断）就留在 `downloads/` 里，下一轮被「清单同步」判成未登记文件——第一次跑红、后面全绿。已改成带 pid 并在每组测试前扫残留。

## 沿用

- 判据只认**磁盘事实**（解包标记 / sha256），不认「上次说下过了」。
- 外部依赖的**路径**由 bz 填进设置、由外部工具包消费；bz 不代管别人的运行环境（Ollama / 模型 / pip）。
- 国内通道只作备用，主通道仍是官方源——镜像不同步时能自然退化，不会静默拿到旧包（sha256 兜底）。
