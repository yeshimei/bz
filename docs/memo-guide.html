一、一句话看懂备忘录 Big Picture

「备忘录」功能就是一本电子便利贴：你在 Obsidian 里记下一件事，它被存成一个 JSON 文件，下次打开时再读出来展示。核心只有 3 个角色：

🖱️你（用户）
点按钮、输入文字
→
🎨ui.ts
界面：弹窗、卡片、按钮
→
📦data.ts
读写 memo.json
→
💾memo.json
数据文件（存磁盘）

中间的 app.ts 是「总管」：负责启动初始化、监听事件、定时检查；due.ts 是「闹钟算法」：判断某件事是否到期；types.ts 是「合同」：规定一条备忘录长什么样。

比喻：这就像一家小餐馆——ui.ts 是前台服务员（接单），data.ts 是后厨（做菜/存菜），app.ts 是店长（开门打烊、安排巡场），memo.json 是账本，due.ts 是挂在墙上的日历。

所有数据都存成 JSON 而不是数据库——这样文件可以直接用记事本打开查看，也是「旧数据零迁移」的保证。

三、一条备忘录长什么样 memo.json · 14 个字段

[
  {
    "id": "todo-8f3k2x",        // 唯一编号
    "title": "给老板发周报",     // 内容/标题
    "scene": "工作",            // 场景：剪藏/工作/学习...
    "priority": "important",    // 重要 or 次要
    "created": "2025-06-14 10:00:00", // 创建时间
    "completed": null,          // 完成时间（null=未完成）
    "due": "2025-06-15 18:00",  // 截止时间（null=无）
    "notePath": "我的/笔记A.md", // 关联的笔记路径
    "notePosition": {"line": 3, "ch": 5}, // 光标位置
    "scriptName": null,         // 代码场景的脚本名
    "courseName": null,         // 公开课场景课程名
    "coursePath": null,         // 课程笔记路径
    "linkedNote": null,         // 内部关联笔记
    "url": "https://..."        // 外部链接（剪藏）
  }
]

为什么要设计成 14 个字段？

这 14 个字段 一个都不能改名字——因为用户旧版本里已经存了同样格式的 memo.json，改了就等于数据损坏（项目铁律第 1 条）。

types.ts 里的合同

export interface MemoItem {
  id: string;
  title: string;
  scene: string;
  priority: string; // important | minor
  created: string;
  completed: string | null;
  due: string | null;
  // ... 其余字段同理
}

注意到 string | null 了吗？这是 TypeScript 的「联合类型」——意思是这个字段要么是字符串，要么没有值。没值用 null 表示，程序里就必须先判断再使用，避免「读了个空」的崩溃。

铁律：界面层读数据时会给缺失字段补默认值（如 priority || 'minor'），旧数据没有的字段也能正常显示。

四、入口：index.ts 42 行 · 懒加载

index.ts 是备忘录域的「大门」。Obsidian 启动时会加载这个文件，但不立即干活——只有你第一次使用备忘录相关命令时才真正初始化。这叫 懒加载（项目 ADR-0003），让插件启动更快。

export async function ensureBz(app) {
  if (MemoApp.initialized) return;  // 幂等：只初始化一次
  await MemoApp.init(getBzSettings());  // 真正开工
}

export function openBzPanel(app) {        // 命令：打开备忘录面板
  void ensureBz(app).then(() => {
    UIManager.showMain(null, false);
  });
}
🎯为什么分两层？
  • 注册命令：main.ts 里统一登记（id 三段式 bz-memo-open-panel），换命令名要同步
  • 执行命令：index.ts 提供回调，先确保初始化再干活
  • 「初始化过没？」用 MemoApp.initialized 一个布尔值判断，重复点命令不会重复初始化
🔌依赖注入小技巧
  • setBzSettingsProvider(fn) 让外部（main.ts）把「读设置的函数」塞进来
  • index.ts 自己不 import 设置模块 → 解耦，测试时可以塞假的
  • 这是项目里所有域的通用套路

due.ts 的到期判断（纯函数）

export function getDueStatus(due) {
  if (!due) return null;      // 没有截止时间
  const dueDate = due.slice(0, 10); // 截出日期部分
  const today = getTodayStr();
  if (dueDate < today) return 'overdue'; // 已过期
  if (dueDate > today) return 'future';  // 未来
  return due <= getNowStr() ? 'overdue' : 'today';
}
为什么字符串可以直接比较大小？日期格式是 YYYY-MM-DD HH:mm，年份在前。字符串按字典序比较时，「2025-06-10」一定小于「2025-06-15」——所以直接 < 就等价于「更早」。这是格式设计带来的免费福利。

⚠️ 已知缺陷（故意保留）：主演计数等 bug 按项目铁律不动——教学也是：先学会，再修。

十、样式提取：从内联到样式表 styles.css 收敛

第一轮精简后，样式仍是「内联」的（写在 JS 里）。第二轮把它们全部提取到 styles.css——代码里只留类名，样式集中管理。

❌提取前：JS 里写样式
// 场景按钮的样式写在代码里
Object.assign(btn.style, {
  padding: '6px 14px',
  borderRadius: '20px',
  background: 'var(--background-secondary)',
  // ... 10 行
});
// 7 个标签重复同一串样式
tag.style.cssText = 'padding:0 8px;border-radius:12px;font-size:11px;...';

问题：样式散落在代码里；改一处颜色要翻代码，标签样式重复 7 遍。

✅提取后：类名 + 样式表
// JS 只管「是什么」
btn.className = 'scene-btn';
tag.className = 'bz-tag bz-tag-course';
/* CSS 只管「长什么样」 */
.scene-btn {
  padding: 6px 14px; border-radius: 20px;
  background: var(--background-secondary);
}
.bz-tag { padding: 0 8px; border-radius: 12px; font-size: 11px; }

视觉归 styles.css，逻辑归 JS——各管各的。

哪些样式留在 JS 里？（功能性样式）

  • display：弹窗的显示/隐藏——show/hide 是行为，不是外观
  • height / overflowY：输入框 auto-grow 的高度是 JS 实时计算的
  • 激活态只切类：classList.toggle('active')，颜色交给 .active 类
测试怎么跟着变？jsdom 不加载样式表，所以「红色背景」这类视觉断言改成了类名断言：expect(tag.classList.contains('important')).toBe(true)。测试仍然验证了「重要条目有正确标记」，只是不再关心具体像素——语义更强了。

行数：ui.ts 1216 → 1099，styles.css +197 行。样式总量没变（逐字等价），但代码里再也看不见一串串 style 了。

九、精简实录：我做了什么 功能零损失

精简前 1936 行 → 精简后 1739 行（-197 行，-10%），1220 个测试全绿。方法不是删功能，而是消灭重复：

🧩提取 1：按钮工厂 makeChoiceBtn

场景按钮和优先级按钮的样式、选中逻辑几乎一样，原来是两份 40 行拷贝。合并成一个工厂：

function makeChoiceBtn(container, cls, value, label, onClick) {
  const btn = createElement('button');
  btn.className = cls;   // scene-btn / priority-btn
  btn.dataset.scene ?? btn.dataset.priority = value;
  btn.onclick = () => {
    clearActive(container, cls);  // 取消其他
    setActive(btn, true);        // 点亮自己
    onClick?.(btn);              // 场景特有逻辑
  };
  container.appendChild(btn);
}
🏷️提取 2：标签样式常量 TAG_BASE

7 个标签（课程/脚本/平台/位置/场景/时间/到期）都有同一串样式尾巴，提取成常量拼接：

const TAG_BASE = 'padding:0 8px;border-radius:12px;font-size:11px;line-height:20px;white-space:nowrap;';

tag.style.cssText = `${TAG_BASE}background:var(--background-secondary);color:var(--text-muted);`;
// 要变的地方只剩背景色和文字色
🔎提取 3：建议列表 attachSuggestion

脚本名建议和课程名建议的过滤/渲染/点击/失焦逻辑几乎一样，合并成一个泛型函数。连课程建议的 data-path 回填也一并保住：

function attachSuggestion<T>(input, sugg, container,
  getList, match, render, onPick) { /* 一次写完，两处复用 */ }
⚙️提取 4：设置项辅助函数

设置弹窗 14 项里，toggle/文本/下拉的「读设置→写回→保存」样板完全相同，抽象成 4 个小函数：

function settingToggle(el, name, desc, value, key, after?) {
  new Setting(el).setName(name).setDesc(desc)
    .addToggle(t => t.setValue(value).onChange(async v => {
      getSettings()[key] = v;
      await saveSettings();
      after?.();
    }));
}
精简的原则（重要）：① 不改数据格式；② 不改 DOM id/类名（外部依赖）；③ 不改文案和视觉；④ 不改已知缺陷。精简只做结构重构，不做行为变更——这正是 1220 个测试存在的意义：它们就是「功能没丢」的证明。
